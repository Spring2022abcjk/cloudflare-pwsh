# P3.4 Plan — CI, Packaging, and Release-Candidate Foundation

## Scope and boundary

P3.4 turns the existing P1–P3.3 validation entry points into a Windows-first,
repeatable CI and package-candidate flow. It does not publish to PowerShell
Gallery, run mutation tests against a real Cloudflare account, or change
projection heuristics/admission semantics.

The formal host baseline is PowerShell 7.6+ and .NET 10 on Windows. Normal CI
uses the pinned local schema checkout described by `build/pinned-schema.json`;
the checkout is created under ignored `ref/` evidence and is verified by Git
revision, schema version, and SHA-256 before it is consumed.

## Existing entry points reused

| Concern | Existing evidence | P3.4 composition |
| --- | --- | --- |
| P1–P2.4 regression | `tools/Invoke-P24Tests.ps1` | Regression job and isolated schema-update validation |
| P3.2 generation/source/help/runtime parity | `tools/Invoke-P32ReadOnlyTests.ps1` | `tools/Invoke-P34DeterministicValidation.ps1` |
| P3.3 D1/D2 staging and coverage contract | `tools/Invoke-P33D2ReadOnlyTests.ps1`, `tests/P33Coverage.Tests.ps1` | Deterministic and coverage jobs |
| Compatibility semantics | P2.4 JSON/Markdown reports | `tools/Invoke-P34CompatibilityGate.ps1` |
| Coverage semantics | P3.3 baseline/report schema | `tools/Invoke-P34CoverageGate.ps1` |
| Host/module smoke | `tests/ModuleSmoke.ps1` | Unit/runtime job; candidate uses `tests/P34PackageSmoke.ps1` |

No second projection or runtime implementation is introduced by this phase.

## CI jobs and gates

`.github/workflows/p34-ci.yml` separates the flow into these jobs:

1. **Build** — provision the formal host, bootstrap the exact schema, restore,
   and build Release.
2. **Deterministic generation** — run P3.2/P3.3 isolated read-only staging,
   P3.3 schema/count/freshness tests, golden/hash checks, and worktree checks.
3. **Unit and runtime smoke** — run the C# runtime contract tests and the
   current module host smoke with mock HTTP.
4. **P1–P2.4 regression** — run the existing complete regression chain.
5. **Compatibility** — produce P2.4 JSON and apply the exact policy in
   `build/p34-compatibility-policy.json`.
6. **Coverage** — produce two independent P3.3 reports, validate the complete
   row schema against canonical `coverage-report.json`, and apply the semantic
   policy in `build/p34-coverage-policy.json` to that same JSON artifact.
7. **Package** — assemble the candidate only after all prior jobs succeed and
   upload it as a CI artifact.

The workflow does not contain a publish step and does not require a
Cloudflare token. The separate `.github/workflows/p34-schema-update.yml` is a
manual workflow-dispatch entry for the isolated pinned-schema update chain.

## Documentation-only CI trigger policy

The selected follow-up design for avoiding unnecessary heavy CI on
documentation-only changes is recorded in
[CI Trigger Policy](./ci-trigger-policy.md). It keeps the workflow and a
stable `CI status` check present for every push/PR event, classifies changed
paths in a lightweight PowerShell job, conditionally skips the existing heavy
jobs only for an explicit documentation allowlist, and fails closed for mixed,
unknown, workflow, schema, build, artifact, license, or source changes.

This policy is **designed but not implemented** in the current P3.4 workflow.
Until a separate implementation changes the workflow and branch protection,
`.github/workflows/p34-ci.yml` continues to run its complete job graph for
documentation commits. The manual schema-update workflow remains independent.

## Compatibility policy

The compatibility gate consumes the typed P2.4 report rather than source text
or generated C# diffs. It rejects malformed reports and unknown impacts. New
breaking changes fail; new potentially breaking changes require manual review
and fail the unattended gate; the four current baseline changes are approved
only by exact identity and impact fields in the checked-in allowlist. An
allowlist entry that is not observed is also rejected, preventing a broad or
stale exception.

The policy is intentionally explicit rather than treating `fullyCompatible`
as the only decision. API, SDK, and PowerShell impact dimensions remain
separate.

## Gate receipts and build provenance

Both policy gates emit one machine-readable receipt. The receipt includes
`schemaVersion`, `gateName`, `gateType`, `status`, the policy path and SHA-256,
the input report filename and SHA-256, and the pinned schema identity
(`revision`, `sourceRevision`, `sourcePath`, and SHA-256). The compatibility
receipt also records the old/new comparison revisions. `New-P34Package.ps1`
re-reads both reports and receipts, requires the exact gate name/type and
`status=Passed` with no violations, and recomputes the checked-in policy and
input-report hashes before staging anything. It also checks the report stage
and source identity against `build/pinned-schema.json`, so a receipt copied
from another candidate is rejected.

The coverage workflow retains `first/coverage-baseline.json` and
`second/coverage-baseline.json` only as discovery/determinism staging. It copies
the selected first result to `coverage-report.json` before `P33Coverage.Tests.ps1`
and the coverage gate run. The receipt, uploaded artifact, package input, and
candidate report therefore share one exact JSON filename and hash. The package
builder rejects a coverage input whose filename is not `coverage-report.json`;
the existing Markdown candidate name remains `coverage-baseline.md`.

For compatibility receipts, the package builder also requires the receipt
filename to equal the actual input report filename, and requires
`comparisonIdentity.oldRevision/newRevision` to match the report's
`oldSourceRevision/newSourceRevision`. Both sides must be canonical lowercase
40-character Git revisions; old and new must differ. The old revision must
match `fixtures/p2.4/openapi-previous-revision.json.previousRevision`, while
the new revision must match both that fixture's `currentRevision` and the
pinned schema revision. This closes the comparison provenance chain without
using the fixture filename as an identity source.

The Release assembly carries
`AssemblyInformationalVersion = 0.1.0+source.<Git revision>` and a net10.0
target-framework attribute. The package builder compares both to the current
checkout. `-SkipBuild` is therefore only a verified fast path: a missing or
stale assembly provenance value fails packaging; it does not trust an
existing DLL based on AssemblyVersion alone.

Compatibility changes use a canonical key containing the change kind, the
family-required identity fields, old/new values, and all three impact
dimensions. Schema changes require `schemaName` and path; operation/projection
changes require `operationId` and path, with `resourcePath` included when
present. Unused identity fields are rejected for the family and omitted
fields never act as wildcards. Duplicate report keys and duplicate allowlist
keys fail the gate.

## Coverage policy

The gate validates the P3.3 schema, unique operation rows, classification
reconciliation, count semantics, deterministic input identity, and repeated
report byte equality. Before applying thresholds, it recomputes the complete
classification histogram from `operations[]`; every reported class must match
that recomputation, unknown classes/count keys fail, and duplicate operation
identity fails. It compares operation identities with the checked-in
baseline and detects:

- silently dropped baseline operations;
- a supported operation becoming unsupported, ambiguous, or manual-review;
- newly ambiguous operations;
- newly manual-review operations; and
- an increase in manual-review rows.

Thresholds are named semantic rules, not hard-coded `Supported == N`
assertions. A schema update must intentionally regenerate and review the
baseline artifact and policy.

## Versioning decision

`Directory.Build.props:VersionPrefix` is the source of truth and currently
contains `0.1.0`. It drives .NET assembly/file/informational versions. The
module manifest keeps its required literal `ModuleVersion`, but
`tools/New-P34Package.ps1` fails if it differs from the source value; this
prevents manifest/assembly/package drift. The package builder also verifies
the net10 target and does not package `System.Management.Automation.dll` or
any PowerShell runtime.

## Candidate layout

The package builder produces an ignored candidate directory with this shape:

```text
artifacts/p34-candidate/
  package/Cloudflare.PowerShell/
    Cloudflare.PowerShell.psd1
    Cloudflare.PowerShell.psm1
    Cloudflare.PowerShell-help.xml
    Cloudflare.PowerShell.dll
  reports/
    compatibility-report.json
    compatibility-gate.json
    coverage-report.json
    coverage-baseline.md
    coverage-gate.json
  build-test-summary.json
  candidate-manifest.json
  Cloudflare.PowerShell.0.1.0.zip
```

The ZIP archive has fixed entry timestamps and sorted entries, so equal inputs
on the same supported host/runtime produce equal archive bytes. This is a
same-host deterministic candidate guarantee, not a Level-2 cross-host or
cross-.NET-patch reproducibility claim. Candidate smoke imports the staged
module from a fresh child `pwsh` process with a repository-independent working
directory and repository paths removed from `PSModulePath`; it resolves
representative commands/help/generated metadata from that candidate path and
executes a local mock pagination call.

## Schema-update workflow

Update `build/pinned-schema.json` and the portable previous-revision fixture in
an explicit schema-update change. Run the manual workflow-dispatch workflow.
It fetches/verifies the pinned checkout, archives the tracked repository into
a temporary root, copies only the pinned schema and version/policy inputs,
runs the P1–P2.4 regression and repeated P3.3 coverage discovery, and applies
both gates without using the current worktree as a build target. A changed
schema therefore produces an explicit baseline/allowlist failure that must be
reviewed and updated deliberately.

## Stop conditions

Do not expand release automation when package smoke needs repo-relative source
files, generation writes the current worktree, a real token is needed for
normal acceptance, packaging requires projection changes, report schemas are
unstable, or any P1–P3.3 regression fails. Fix the underlying boundary first.

## Acceptance gates

- Windows PowerShell 7.6+ and .NET 10 are verified.
- Pinned schema revision, source version, and hash agree.
- Existing P3.2/P3.3 isolated gates and P1–P2.4 regression pass.
- Compatibility and coverage reports are deterministic and policy-evaluated.
- Package assembly independently verifies Passed gate receipts, policy/report
  hashes, pinned schema identity, and current assembly provenance.
- Coverage histograms are recomputed from operation rows and compatibility
  identity matching is exact and one-to-one.
- Two package assemblies are byte-identical for equal inputs.
- Candidate content is exact and contains no build/test/runtime payloads.
- Candidate import, commands, help, generated metadata, assembly location, and
  mock/local runtime smoke pass.
- The current worktree is unchanged by the read-only validation/tests.
- No PowerShell Gallery publish or real-account acceptance is claimed.
- Remote GitHub Actions execution has not been evidenced locally; action
  full-SHA pinning remains future supply-chain hardening.
