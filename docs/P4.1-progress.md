## Chosen pipeline design

The module registers two generated, PowerShell-only ETS AliasProperty entries
from canonical pipeline-identity metadata:

| Type | Alias | Source | Use |
|---|---|---|---|
| CfZone | ZoneId | Id | Zone resource identity |
| CfDnsRecord | DnsRecordId | Id | DNS-record resource identity |

This makes the following workflow real and tested:

    $zone | Get-CfDnsRecord

The parent/scope boundary remains explicit:

    $record | Get-CfDnsRecord -ZoneId $zone.ZoneId
    $record | Set-CfDnsRecord -ZoneId $zone.ZoneId -Edit @{ Content = '192.0.2.10' }
    $record | Remove-CfDnsRecord -ZoneId $zone.ZoneId -WhatIf

The module does not infer ZoneId from CfDnsRecord.Id, name, or content.
Record-only mutation fails before dispatch because ZoneId is still mandatory.

Option B was rejected because PowerShell accepts a parameter AliasProperty for
pipeline-by-property-name binding, but rejects declaring Id as an alias for
both ZoneId and DnsRecordId in the same command. Options A and D would pollute
the API/model or replace the typed output shape. Option E would remove a
useful supported workflow. The complete comparison and evidence are in
[P4.1-pipeline-identity-design.md](P4.1-pipeline-identity-design.md).

## Compatibility implications

The change is additive at the PowerShell projection boundary:

- Pipeline binding becomes truthful for the two resource identities.
- Generated C# model properties remain unchanged.
- Existing parameter names, aliases, mandatory flags, parameter sets,
  ShouldProcess actions, ConfirmImpact values, output types, and HTTP
  construction remain unchanged.
- PowerShell Get-Member, ConvertTo-Json, and PSSerializer expose the ETS
  aliases as extended members. This is a documented, tested compatibility
  consideration.
- No parent scope is synthesized.

The P2.4 synthetic suite recognizes PipelineBindingChanged as a compatibility
category. No existing public parameter metadata was changed in this phase;
the ETS aliases are therefore tracked as projection UX behavior rather than a
normalized API-schema change. The current P2.4 projection comparison is
identity/empty for the existing command metadata, which is the expected result
because the declarations were already present. P2.4 does not model session ETS
members, so the additive serialization/output consideration is explicitly
covered by the P4.1 host and candidate tests rather than silently treated as
an API-model change.

## Help model changes

The projection policy now carries PowerShell-specific help metadata for every
admitted cmdlet:

- syntax and parameter-set descriptions;
- descriptions for every projected user parameter;
- typed input and output entries;
- examples and remarks;
- a stable Cloudflare API related link.

The generator emits complete MAML from that metadata. It does not hand-edit
the generated XML. Help includes the typed DNS input variants
CfARecordInput, CfMxRecordInput, CfCaaRecordInput, CfHttpsRecordInput, and
CfSvcbRecordInput; Set Edit versus Replace/PATCH versus PUT semantics; Remove
no-output behavior; and WhatIf/ShouldProcess guidance.

The help descriptions deliberately distinguish projection initializers,
pagination-internal behavior, explicitly bound values, and API-side defaults.
They do not claim that Match, TagMatch, Proxied, Page, or PerPage values are
all Cloudflare API defaults.

## Help completeness

Fresh candidate checks show all five commands have non-empty:

- Get-Help and Get-Help -Full synopsis/description;
- Get-Command -Syntax;
- MAML syntax items for every parameter set;
- parameter help and documented aliases;
- INPUTS and OUTPUTS sections;
- examples, with PowerShell parser validation;
- related links.

Remove-CfDnsRecord documents a None output entry rather than an empty OUTPUTS
section. The module does not claim updateable online help because no stable
HelpInfoURI policy exists yet.

## Remaining UX and formal blockers

The two Phase 0 implementation blockers are resolved in the candidate. The
remaining release blocker is downstream gate freshness: P3.3 D2 isolated
reproduction reports drift in `artifacts/p3.3/CmdletModel.json`, and the P3.4
schema-update coverage gate reports that the frozen coverage baseline contains
the pre-P4.1 `publicArtifact` identity. The requested finalization did not
refresh a baseline or compatibility allowlist.

Manual review of help wording and display width remains a separate acceptance
item. Formatting and custom completion remain deferred.

## Deferred formatting and completion

Built-in parameter completion remains available. No custom argument completer,
ValidateSet restriction, format.ps1xml, or custom type view was added. The
Phase 0 evidence did not establish a stable value set or a sufficiently
high-value display contract, so these are deferred rather than guessed.
