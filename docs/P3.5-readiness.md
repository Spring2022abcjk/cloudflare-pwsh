# P3.5 Real Integration Readiness

## Decision summary

This is a Phase 0 inventory only. No Cloudflare resource was created,
modified, or deleted, and no high-volume request pattern was used.

| Slice | Decision | Boundary |
| --- | --- | --- |
| P3.5a read-only live validation | **Ready, scope-limited** | Use the account-scoped `CF_API_WACS_TOKEN` only after the visible account and zone are confirmed by the owner as test-approved. DNS list/read is live-verified; broader resources remain unverified. |
| P3.5b constrained CRUD | **Not ready** | No mutation authorization, test-only account/zone confirmation, naming protocol, or cleanup approval is present. No DNS mutation was attempted. |
| P3.5c transport/rate-limit/error | **Not ready for the full slice** | Passive rate-limit headers and ordinary 401/403 behavior are observable, but 429 generation is forbidden, multipart/binary/no-content resources are not safely available, and DNS export has a live media-type drift. |

The recommended order is **P3.5a → P3.5b → P3.5c**. P3.5b must not start
until the mutation boundary is explicitly approved. P3.5c should first resolve
the transport-contract finding and use mock tests for any scenario that would
otherwise require inducing load or mutation.

## Read-only validation scope

Allowed now, subject to the owner confirming the selected account/zone:

- token verification using the matching user-level or account-level endpoint;
- account and zone listing with bounded page sizes;
- `Get-CfDnsRecord` against the explicitly selected zone;
- DNS record pagination and response/error observation;
- Health Check and D1 list attempts only when explicit approved IDs are
  supplied, retaining 401/403 as evidence rather than retrying aggressively;
- DNS export as a read-only raw-body candidate, without persisting its body.

The current live cmdlet check passed for `Get-CfDnsRecord` and returned `15`
records. This is supplementary live evidence; it does not replace the existing
mock/runtime contract tests.

## Allowed mutation scope

There is **no allowed mutation scope in Phase 0**. In particular, the current
inventory does not authorize DNS create/update/delete, D1 CRUD, Health Check
CRUD, import/upload, rate-limit configuration, or any other POST/PUT/PATCH/
DELETE operation.

For a future P3.5b run, the only proposed scope is explicitly approved DNS CRUD
on a disposable or reversible resource in an owner-confirmed test zone. The
approval must name the account/zone out of band, identify the token permission,
authorize the exact operations, and approve the cleanup procedure. DNS Read
success must not be interpreted as DNS Write authorization.

## Forbidden scope

- Any create, update, patch, replace, import, upload, or delete request.
- Any request using an unconfirmed production zone or account.
- D1 or Health Check mutation, even if a future read probe succeeds.
- Creating a temporary DNS record merely to test transport, retry, or 429
  behavior.
- High-rate loops or concurrent bursts intended to manufacture HTTP 429.
- Changing runtime, retry, idempotency, public cmdlet, normalized contract, or
  release policy behavior as a response to live findings.
- Recording token values, token IDs, account IDs, zone IDs, domains, record
  contents, or raw export content in source, logs, artifacts, or summaries.

## Secret-handling rules

- Read tokens only from the existing environment-backed mechanism.
- Do not accept or recommend command-line token arguments for reproducible runs.
- Construct the `Authorization` header in process memory only.
- Never print headers, request objects, exception bodies, token metadata IDs, or
  raw response content.
- Keep live counts/statuses separate from deterministic fixtures and package
  artifacts.
- Treat `CF_API_TOKEN` and `CF_API_WACS_TOKEN` as distinct credentials; do not
  silently substitute one for the other.
- If a failure body could contain account or resource details, record only HTTP
  status and a generic exception class.

## Cleanup strategy

P3.5a is read-only and has no cleanup requirement. The current run created no
residue.

Before any future P3.5b mutation is authorized, freeze a pre-test inventory and
agree on all of the following out of band:

1. a deterministic name prefix such as `p35b-real-<run-id>` that cannot collide
   with existing records;
2. a single approved record type and exact reversible values;
3. recording the created resource ID only in the ephemeral test runner, never
   in repository output;
4. delete-in-finally behavior after successful create/update assertions; and
5. a post-run list filtered by the prefix, with an interruption scan before a
   new run.

If creation reports failure but may have succeeded, stop and perform an exact
prefix/ownership scan before retrying. If cleanup fails or the scan is
ambiguous, stop all further mutation and require manual cleanup. No bulk delete
or broad name-based cleanup is acceptable.

## Rate-limit and retry candidates

Low-volume ordinary requests exposed the current REST headers without inducing
load:

- `Ratelimit: "default";r=1199;t=1`,
  `Ratelimit-Policy: "default";q=1200;w=300` on account-list calls;
- `Ratelimit: "list_zones";r=1200;t=1`,
  `Ratelimit-Policy: "list_zones";q=1201;w=300` on zone-list calls; and
- no `Retry-After` header, because no 429 response occurred.

These are time-of-probe observations, not a quota guarantee. Cloudflare
currently documents a global client API limit of 1,200 requests per five
minutes per user/account token and defines `Ratelimit`, `Ratelimit-Policy`, and
429-only `Retry-After` headers in its [rate-limit reference](https://developers.cloudflare.com/fundamentals/api/reference/limits/).

Safe candidate work:

- continue recording headers from already-required, low-volume read calls;
- validate 429 parsing, backoff, and jitter with mock transport tests; and
- use a provider-approved low-impact test mechanism only if Cloudflare or the
  account owner supplies one.

Blocked/deferred work:

- deliberately generating 429 with loops, bursts, parallel calls, or repeated
  pagination;
- treating an absent `Retry-After` on a 200 response as evidence about 429
  behavior; and
- testing mutation retry/idempotency live without explicit idempotency scope.

## Blocked scenarios

1. The default `CF_API_TOKEN` is active but sees no accounts or zones.
2. The account-scoped `CF_API_WACS_TOKEN` is usable for one account and two
   zones, but its test-only status has not been confirmed.
3. D1 list is 401 and Health Check list is 403; neither permission is admitted.
4. No explicit account/zone IDs are configured; the probe intentionally avoids
   substituting discovered IDs for future runs unless the owner selects them.
5. DNS export live media type differs from the pinned normalized contract.
6. Multipart candidates are mutating; binary download requires deeper resource
   identifiers; no-content and true streaming evidence are unavailable.
7. No safe method exists in this environment to induce 429 without risking
   account-wide throttling; 429 remains deferred.
8. Token verification does not enumerate the full effective permission policy,
   and successful reads cannot distinguish read-only from write permission.
9. HTTP `2xx` with `success=false` remains an existing unresolved semantic and
   is not decided by this inventory.

## Risks

- The visible zones may be production or shared zones. Counts alone are not
  proof of disposability.
- Using the wrong token for a phase could make an account-token 401 look like a
  general authentication failure, or could accidentally broaden scope.
- Content-type-based response selection may diverge from the pinned contract on
  live endpoints; the DNS export finding is the first concrete example.
- Account/zone/resource counts and rate-limit headers are mutable snapshots and
  must not be promoted to deterministic fixture evidence.
- Live DNS records can contain operationally sensitive names/content; only
  counts were retained.
- P3.1 retry and idempotency mock evidence does not establish live retry safety.

## Recommended entry gates

### P3.5a

Proceed with a read-only pilot only after the owner records, outside the repo,
that the account-scoped token and selected zone are approved for testing. Use
the sanitized probe plus `Get-CfDnsRecord`; retain counts/statuses and bounded
error evidence only. Do not add the export response body to an artifact.

### P3.5b

Do not start yet. First obtain explicit mutation authorization, confirm a
test-only/disposable zone, approve the naming and cleanup protocol, and prove
that the token has DNS Write. The first run should be DNS-only and serial,
with create → read → update/edit → read → delete → cleanup scan. D1 and Health
Check CRUD remain outside this readiness result.

### P3.5c

Do not claim full readiness yet. First decide whether the live DNS export
media-type difference is an acceptable endpoint variation or a contract issue,
then select an approved binary/streaming resource if one exists. Keep 429
validation deferred unless a low-impact provider-approved method is supplied;
continue using mocks for induced 429, retry, idempotency, and no-content cases.
