# P3.3 Coverage Expansion Progress

This progress log records the completed discovery slice separately from the
future public-surface expansion. It does not claim full API coverage,
real-account validation, packaging, release, or device/manual acceptance.

## Implemented

- Added `tools/Invoke-P33CoverageDiscovery.ps1`, which calls the existing
  loader, normalizer, correction engine, and projection builder.
- Added a deterministic operation-level classification contract covering
  normalization, corrections, projection conflicts, runtime capability gaps,
  bounded public admission, and manual review.
- Added complete JSON and human-readable Markdown baseline reports under
  `artifacts/p3.3`.
- Added `docs/P3.3-plan.md` with dependencies, report schema, D1 extension
  scope, acceptance gates, correction/model/projection decisions, and stop
  conditions.
- Updated architecture, roadmap, README, and development principles with the
  P3.3 discovery boundary.

## Validated

- Pinned source revision `4.0.0` normalized to `3,407` operations and `67,486`
  schemas.
- All `3,407` operations received exactly one final classification.
- Two operations carry an API correction trace; eight operations are in the
  current public surface across five cmdlets.
- The baseline reports `3,382` runtime-ready stage operations, `25` runtime
  capability-gap stage rows, `568` projection conflicts, `10` final
  `UnsupportedRuntimeCapability` classifications, and `617` low-confidence
  manual review operations.
- The selected first expansion family, `d1/database`, contains six
  high-confidence, runtime-ready operations, including the partial-update
  operation.
- Discovery output omits wall-clock values and is intended for byte-stable
  regeneration.
- The P3.3 report schema/count test passed, and two isolated discovery runs
  produced identical JSON/Markdown hashes.
- Coverage freshness now compares fresh JSON/Markdown to both the checked-in
  baseline artifacts and each other, including source/input identity and
  schema/operation counts; negative sourceRevision and count mutations fail
  the gate.
- P3.2 portable input hashing now canonicalizes UTF-8 text line endings;
  projector/generator parity, isolated Release build, mock/runtime smoke, and
  P1--P2.4 regression acceptance all pass across the CRLF/LF boundary.

  PATCH use separate typed body parameters and the `PartialUpdate` parameter
  set.
- Added `tests/P33D1Projection.Tests.ps1`, `tests/P33D1Smoke.ps1`, and

  contracts, source-boundary review, mock HTTP behavior, and isolated

- The P3.3 read-only entry point now declares its own exact input set and uses
  the shared `tools/ReadOnlyStaging.ps1` engine. It stages only the pinned

- Added `tools/Invoke-P33D1Compatibility.ps1` and the deterministic
  `artifacts/p3.3/d1-projection-compatibility.{json,md}` report; the existing
  projection compatibility engine exposes the new `PartialUpdate` public

## Still Deferred

- Full projection/model capability needed to admit new resource families.
- Complete real-account, device/manual, packaging, publishing, and release
  evidence.
- Unresolved runtime semantics such as `2xx + success=false`, legacy auth,
  automatic idempotency, and complete mutation retry safety.
- P2.4 standalone mode still supports a Git-history fallback when no portable
  revision manifest is supplied. Canonical P3.2 acceptance does not use this
  path. Consider removing the fallback if full repository-independent
  execution becomes a requirement.
