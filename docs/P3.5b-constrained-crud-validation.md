# P3.5b — Constrained CRUD Validation

## Status

**未开始；文档准备完成，等待具体授权。** No DNS create, update, or delete
has been executed. This document defines the authorization and execution
boundary; it is not a readiness, completion, or real-account mutation result.

## Task goal

Validate the admitted DNS CRUD path in one explicitly approved
test-only/disposable or reversible Cloudflare zone, while preserving a precise
scope and a recoverable cleanup path. The task must not begin until the
specific mutation authorization described below exists.

## Scope

The only live sequence in scope is:

`DNS create → read → update/edit → read → delete`

- One explicitly approved zone, serial execution, and one test record or the
  smallest approved number of records.
- The record type, value, and deterministic test-name prefix are fixed before
  execution.
- D1, Health Check, import, upload, and bulk mutation are out of scope.
- Read-only evidence and mock/local evidence remain separate from the real
  account result.

## Required authorization before start

All of the following must be confirmed before any mutating request:

1. The exact account and zone are named in the authorization record, with the
   selected scope confirmed by the owner.
2. The zone is explicitly test-only/disposable or its reversibility and owner
   approved cleanup procedure are documented.
3. The token has an independent proof of DNS Write permission. Successful
   authentication or DNS Read/list access is not sufficient evidence of DNS
   Write.
4. The allowed HTTP methods and concrete create, read, edit/update, and delete
   operations are explicitly listed.
5. The record type, value, owner, and deterministic name prefix are fixed;
   the prefix must not overlap unrelated records.
6. A fresh candidate built from the current HEAD passes package smoke,
   provenance, and the formal five-command check. The public surface remains
   exactly `Get-CfZone`, `Get-CfDnsRecord`, `New-CfDnsRecord`,
   `Remove-CfDnsRecord`, and `Set-CfDnsRecord`; D1/D2 remain test-only.
7. All credentials are injected through the existing environment variables.
   Credentials must never be written to the repository, artifacts, reports, or
   logs.

## Execution protocol

Run serially and keep resource identifiers in process memory only:

1. **Pre-test inventory** — perform a zone-scoped exact scan for the approved
   deterministic prefix and owner; record only the allowed sanitized counts.
2. **Create** — issue the single approved DNS create operation and record the
   sanitized result.
3. **Read** — retrieve the created record through the approved read path and
   verify the expected presence and typed result semantics.
4. **Edit/update** — issue the explicitly approved edit/update operation with
   the pre-approved value change.
5. **Read** — retrieve the record again and verify the updated presence/value
   semantics without persisting the value or identifiers.
6. **Delete** — delete only the exact record established by the approved
   sequence, subject to `ShouldProcess`/confirmation behavior.
7. **Cleanup scan** — perform a final exact prefix-and-owner scan and record
   the sanitized zero-residue result or stop with a cleanup failure.

## Cleanup and stop rules

- The delete and final cleanup scan must be protected by `finally`, including
  failures after create, read, or update.
- If create times out or its result is otherwise uncertain, do not retry
  immediately. First perform an exact zone-scoped scan by the deterministic
  prefix and owner; resolve the result under the approved protocol before any
  retry or cleanup action.
- Stop immediately on cleanup failure, any ambiguous scan result, multiple
  possible owners/targets, a target that no longer matches the approval, or a
  zone/scope mismatch. Preserve the sanitized failure evidence and request
  operator review.
- Never use bulk delete, a broad name match, an unbounded prefix deletion, or a
  delete against a target whose identity was inferred rather than established
  by the approved sequence.

## Evidence requirements

Record only status codes, the API success flag, error category, non-sensitive
provider code, counts, and timestamps. Do not record tokens, account IDs, zone
IDs, domains, record IDs, record names, record content, or raw response bodies.

Keep these evidence classes separate:

| Evidence class | What it may establish | What it may not establish |
| --- | --- | --- |
| Code and mock/local | Contract, `ShouldProcess`, WhatIf, confirmation, presence/null, and failure-path behavior. | Real-account permission or mutation success. |
| Candidate/package | Current-HEAD identity, package smoke, provenance, and formal five-command surface. | Real-account CRUD or cleanup. |
| Real account | The specifically authorized single-zone CRUD sequence and sanitized provider outcomes. | Broad account capability, other zones, or transport scenarios outside the run. |
| Cleanup | Exact final scan and no-residue result, or a bounded cleanup failure. | Permission to broaden deletion or retry ambiguously. |

## Acceptance criteria

P3.5b can be accepted only when all of the following are evidenced:

- Create → read → edit/update → read → delete passes for the approved scope.
- Presence/null semantics match the expected contract at each read boundary.
- `ShouldProcess`, WhatIf, and confirmation behavior have explicit evidence.
- Failure paths and the `finally` cleanup path have explicit evidence.
- The final exact scan proves no residual test records.
- Real-account evidence is stored separately from code, mock/local, and
  candidate/package evidence.

## Explicit exclusions

- Do not manufacture or validate 429 responses.
- Do not modify the runtime, normalizer, retry policy, idempotency behavior, or
  public API.
- Do not expand the task into P3.5c, P4.3, PowerShell Gallery, or release
  validation.
