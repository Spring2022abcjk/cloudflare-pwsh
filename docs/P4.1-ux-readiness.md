# P4.1 Phase 0 — Manual PowerShell UX / Help Readiness

## 结论

当前五个正式 public cmdlet 的生成、导入、mock runtime 和基础
`ShouldProcess` 行为可用，但当前 candidate 还不能算 PowerShell UX / Help
ready。最明确的发布前问题是：

1. 五个 cmdlet 的 MAML 帮助只有 synopsis 和 description；`Get-Help -Full`
   的 SYNTAX、PARAMETERS、INPUTS、OUTPUTS、RELATED LINKS 均为空，没有
   parameter help、examples 或 online-help link。
2. `Get-CfZone` 输出 `CfZone.Id`，而 `Get-CfDnsRecord` 的 mandatory
   `ZoneId` 只声明了 `ValueFromPipelineByPropertyName`。因此用户要求的
   `$zone | Get-CfDnsRecord` 实际不能绑定。
3. typed DNS request input、Set 的 Edit/Replace 选择和大量 DNS list filters
   没有帮助引导；用户必须阅读源码/类型名才能构造可靠调用。

输出类型、mock error mapping 和 mutation WhatIf 本身有可接受的基础行为。
自定义 completer 和 format view 当前没有实现，但不是自动的发布 blocker；
应在补齐帮助后按真实用户价值决定。

## Current public surface

The candidate exports exactly:

```text
Get-CfZone
Get-CfDnsRecord
New-CfDnsRecord
Remove-CfDnsRecord
Set-CfDnsRecord
```

No D1/D2 bounded test cmdlet is exported. The manifest and generated command
surface agree with the public-admission policy. `BaseUrl`, `Token`, and
`Handler` are hidden infrastructure parameters for local/mock injection; they
are not treated as end-user UX.

## Per-command UX findings

Status terms in this document are evidence status, not implementation status:
`Complete`, `Partial`, `Missing`, and `Incorrect`.

### `Get-CfZone`

- Naming: Complete. `Get-CfZone` is a natural resource-oriented name.
- Parameter sets: Partial. `List` is the default and `Get` requires `ZoneId`,
  which is understandable, but syntax is absent from help.
- Mandatory parameters: Complete for the current contract. List has no
  mandatory filter; Get requires `ZoneId`.
- Parameter names: Partial. `AccountId`, `AccountName`, `Name`, `Status`, and
  `Type` are recognizable; `Direction`, `Match`, and `Order` are unconstrained
  strings with no allowed-value guidance.
- Aliases: Complete. No alias is clearly needed.
- Pipeline: Incorrect for the requested zone-to-DNS workflow; output exposes
  `Id`, not `ZoneId`.
- ShouldProcess: Complete. Read-only list/get does not advertise confirmation.
- Defaults: Partial. The projection records `Match=all`, `Page=1`, and
  `PerPage=20`, but help does not disclose them. The paginator adds `page=1`
  to the mock request; other defaults are not visible to the user.
- Output: Partial. Typed `CfZone` output is good and the default table is
  compact (`Id`, `Name`, `Status`, `Type`), but the fields are not documented.
- Errors: Partial. Stable Cloudflare error identity/category is present, but
  there is no command-specific recovery guidance.
- Help/discoverability: Partial at command level, Missing for syntax,
  parameters, examples, and links.

### `Get-CfDnsRecord`

- Naming: Complete. The singular noun is consistent with the CRUD commands.
- Parameter sets: Partial. `List` and `Get` are logical, but List exposes a
  large filter surface (`Comment*`, `Content*`, `Name*`, `Tag*`, shadowing
  filters) without grouping or examples.
- Mandatory parameters: Complete for the current contract. `ZoneId` is
  mandatory for both sets; `DnsRecordId` is mandatory only for Get.
- Parameter names: Partial. The `*Contains`, `*Exact`, `*Startswith`, and
  `*Endswith` names are discoverable, while `TagMatch`, `TagAbsent`,
  `ShadowedByName`, and `ShadowingName` need explicit explanations.
- Aliases: Complete. `RecordId` is a clear compatibility alias for
  `DnsRecordId`, but it is not documented by `Get-Help`.
- Pipeline: Incorrect for common object chaining. The cmdlet accepts
  `ZoneId`/`DnsRecordId` by property name, but `CfZone` has `Id`; a `CfDnsRecord`
  has `Id` and no `ZoneId`/`DnsRecordId`. The declared pipeline contract and
  emitted object properties do not line up.
- ShouldProcess: Complete as read-only behavior. No confirmation is expected.
- Defaults: Partial and needs manual semantic review. The projection records
  `Direction=asc`, `Match=all`, `Order=type`, `Page=1`, `PerPage=100`,
  `Proxied=false`, and `TagMatch=all`; the no-filter mock request showed only
  paginator `page=1`. Whether the other values are intended PowerShell
  defaults or API-side defaults must be made explicit before changing them.
- Output: Partial. Typed `CfDnsRecord` output is correct, but default formatting
  expands many nullable fields as blank properties (`Ttl`, `Proxied`, `Data`,
  `Comment`, `Tags`, timestamps), which is readable but noisy.
- Errors: Partial. A mock 400 produced `Cloudflare.Api.400`, category
  `InvalidArgument`, target `zone`, and the API code/message. This is useful
  diagnostic data but lacks parameter/filter context.
- Help/discoverability: Partial at command level, Missing for syntax,
  parameter meanings, examples, and links. This is the highest UX risk because
  the filter surface is large.

### `New-CfDnsRecord`

- Naming: Complete. `New` is appropriate for creation.
- Parameter sets: Complete. One `Create` set is simple.
- Mandatory parameters: Complete for the current contract. `ZoneId` and typed
  `Record` are required.
- Parameter names: Partial. `Record` is reasonable, but its abstract input
  type requires users to discover `CfARecordInput`, `CfMxRecordInput`,
  `CfCaaRecordInput`, `CfHttpsRecordInput`, and `CfSvcbRecordInput` elsewhere.
  `IncludeShadowMetadata` is not self-explanatory.
- Aliases: Complete. No alias is clearly needed.
- Pipeline: Partial. `ZoneId` accepts property-name pipeline input, but the
  request body does not accept pipeline input; this is defensible but must be
  shown in examples.
- ShouldProcess: Complete. `ConfirmImpact=Medium`; direct WhatIf text was
  `What if: Performing the operation "Create DNS record" on target "zone".`
- Defaults: Partial. `IncludeShadowMetadata` defaults to false but is not
  documented.
- Output: Complete for the current contract. A successful mock create returns
  one typed `CfDnsRecord` object.
- Errors: Partial. Stable error mapping exists; help does not explain common
  validation/authentication failures.
- Help/discoverability: Partial at command level, Missing for typed body
  construction, parameters, examples, and links.

### `Remove-CfDnsRecord`

- Naming: Complete. `Remove` and singular `CfDnsRecord` are natural.
- Parameter sets: Complete. One `Delete` set is simple.
- Mandatory parameters: Complete for the current contract. `ZoneId` and
  `DnsRecordId` are required.
- Parameter names/alias: Partial. `RecordId` is a clear compatibility alias;
  the canonical `DnsRecordId` is precise but not introduced in help.
- Pipeline: Partial in metadata, Incorrect in common chaining because emitted
  record/zone objects do not expose the required property names.
- ShouldProcess: Complete. `ConfirmImpact=High`; WhatIf emitted
  `What if: Performing the operation "Delete DNS record" on target "record".`
  and made no mock HTTP request.
- Defaults: Complete. There is no accidental delete without explicit IDs.
- Output: Complete for the current contract. `outputPolicy=none` and the mock
  delete produced no object; this is intentional and must be documented.
- Errors: Partial. Stable mapping exists, but no help explains that a
  successful delete has no output.
- Help/discoverability: Partial at command level, Missing for syntax,
  parameters, examples, output behavior, and links.

### `Set-CfDnsRecord`

- Naming: Complete. `Set` is recognizable for update/edit behavior.
- Parameter sets: Partial. `Replace` is the default and `Edit` is the
  alternate; both are mutually exclusive mandatory Hashtable bodies. The
  distinction is technically clear in metadata but not user-clear without
  help, especially because the input body is untyped.
- Mandatory parameters: Complete for the current contract. Both sets require
  `ZoneId`, `DnsRecordId`, and exactly one body parameter.
- Parameter names/alias: Partial. `RecordId` is clear; `-Edit @{...}` and
  `-Replace @{...}` need examples and field guidance.
- Pipeline: Partial in metadata, Incorrect for direct chaining from the
  current typed output objects for the same property-name reason.
- ShouldProcess: Complete. `ConfirmImpact=High`; direct WhatIf text was
  `Edit DNS record` or `Replace DNS record` on the record ID.
- Defaults: Partial. `Replace` is the default set and
  `IncludeShadowMetadata=false`, but neither is explained by help.
- Output: Complete for the current contract. Mock edit returned one typed
  `CfDnsRecord`.
- Errors: Partial. Stable error mapping exists but no operation/set-specific
  recovery guidance is available.
- Help/discoverability: Partial at command level, Missing for set selection,
  body shape, parameters, examples, and links.

## Pipeline findings

The current metadata advertises property-name pipeline binding for:

| Cmdlet | Declared pipeline properties |
|---|---|
| Get-CfZone | `ZoneId` in Get |
| Get-CfDnsRecord | `ZoneId` in List/Get; `DnsRecordId` in Get |
| New-CfDnsRecord | `ZoneId` |
| Remove-CfDnsRecord | `ZoneId`, `DnsRecordId` |
| Set-CfDnsRecord | `ZoneId`, `DnsRecordId` |

The representative workflow reproduced the mismatch:

```powershell
$zone = Get-CfZone -BaseUrl ... -Token ... -Handler $handler
$zone | Get-CfDnsRecord -BaseUrl ... -Token ... -Handler $handler
```

The first command returned `Cloudflare.PowerShell.CfZone` with `Id=zone`. The
second failed before HTTP dispatch with the standard PowerShell message that
the input object could not bind to any pipeline parameter. This is a concrete
behavioral UX defect, not merely a documentation preference.

The same property mismatch is likely to affect direct chaining from
`CfDnsRecord` into `Remove-CfDnsRecord` or `Set-CfDnsRecord`: the output has
`Id`, while consumers require `DnsRecordId`, and it has no `ZoneId`. This
follow-up should be confirmed with an explicit workflow test before selecting
an implementation.

## Output and error findings

- `Get-CfZone`, `Get-CfDnsRecord`, `New-CfDnsRecord`, and `Set-CfDnsRecord`
  expose typed output metadata and returned the expected typed objects in the
  mock walkthrough.
- `Remove-CfDnsRecord` has no output type and emitted no object. This matches
  the canonical `outputPolicy=none`; the absence is intentional but currently
  undocumented.
- The default `CfZone` display is compact and usable.
- The default `CfDnsRecord` display is the generic property view and includes
  many blank nullable properties. It is readable but not optimized for a
  first-time user.
- A mock HTTP 400 surfaced a stable `Cloudflare.Api.400` error identity,
  `InvalidArgument` category, target `zone`, and Cloudflare code/message. This
  is good diagnostic foundation. Help still needs to explain how to interpret
  status, code, and target.

## Completion / formatting findings

- Built-in PowerShell parameter completion works: `TabExpansion2` for
  `Get-CfDnsRecord -` returned 38 parameter candidates.
- No custom `ArgumentCompleter` / `Register-ArgumentCompleter` implementation
  was found.
- No enum/value completion was found; most filter values are unconstrained
  strings. Adding `ValidateSet` or value completers without confirming the API
  contract could become a behavioral restriction.
- No module `format.ps1xml`, custom type view, or `DefaultDisplayPropertySet`
  was found. `Get-FormatData -TypeName Cloudflare.PowerShell.CfDnsRecord`
  returned no module-specific view.
- Custom completion and formatting have real potential value, but they should
  follow the help and pipeline fixes. They are not assumed mandatory solely
  because they are absent.

## Compatibility sensitivity and potentially breaking changes

These are recommendations only; none was implemented in Phase 0.

| Potential change | Classification | Phase 0 decision |
|---|---|---|
| Rename a public cmdlet | Breaking | Defer; do not change names |
| Rename `DnsRecordId`, `ZoneId`, `Edit`, or `Replace` | Breaking / potentially breaking | Defer; preserve aliases and contract |
| Redesign `List`/`Get` or `Edit`/`Replace` parameter sets | Potentially breaking | Defer to explicit projection/compatibility review |
| Make an optional parameter mandatory | Potentially breaking | Defer |
| Change pipeline binding or emitted property names | Behavioral to potentially breaking | Requires dedicated pipeline compatibility evidence |
| Change output type or Remove no-output policy | Breaking | Defer |
| Change ShouldProcess target/action or ConfirmImpact | Behavioral / potentially breaking | Defer; current safety behavior is acceptable |
| Add parameter descriptions/examples/help XML | Non-breaking polish | Recommended first |
| Add a non-restrictive value completer | Non-breaking polish | Consider after API value evidence |
| Add a custom format view without changing object shape | Non-breaking polish | Consider after output review |

The pipeline mismatch can potentially be addressed by an additive property
alias/adapter, but the correct solution is not selected here. Any solution
that changes accepted pipeline inputs or serialized output must be checked as
a `PipelineBindingChanged` / output compatibility concern.

## Non-breaking improvement candidates

### Must fix before release

- Generate complete MAML help for all five commands: syntax, parameter
  descriptions, parameter-set semantics, inputs/outputs, examples, and
  related/online links where a stable target exists.
- Make the documented pipeline story truthful. Either provide an evidence-backed
  zone/record property mapping or explicitly mark the unsupported workflow;
  the current metadata implies a workflow that fails.
- Add help explaining typed DNS input variants, omitted versus explicit values,
  `Edit` versus `Replace`, `Remove` no-output behavior, and the destructive
  WhatIf/Confirm behavior.

### Should fix before release

- Document defaults and filter semantics, especially `Proxied=false`,
  `TagMatch=all`, `Match=all`, and the paginator's page behavior. Resolve the
  distinction between projection defaults and API-side defaults before making
  runtime changes.
- Add at least one safe mock-backed example per cmdlet, including the exact
  `-Record` typed construction pattern and both Set parameter sets.
- Add error interpretation guidance for status, Cloudflare error code,
  `FullyQualifiedErrorId`, category, and target.

### Nice to have

- Add a compact DNS record type view or a documented `Select-Object` recipe
  after reviewing whether blank nullable fields are materially harmful.
- Add constrained value completers for filters only where the API contract and
  compatibility policy prove a stable value set.
- Add a small discoverability section to module help linking the five commands
  by CRUD workflow.

### Defer

- Command/parameter renames, parameter-set redesign, output-shape changes,
  mandatory changes, and new public cmdlets.
- Broad pipeline-by-value support or implicit object transformation until a
  complete object identity/scope policy is agreed.
- Online help links if the public documentation location and versioning policy
  are not yet established.

## Blocked / manual-review items

- The intended identity mapping between `CfZone.Id` and `ZoneId`, and between
  `CfDnsRecord.Id` plus zone scope and `DnsRecordId`/`ZoneId`, needs a product/API
  decision before changing pipeline behavior.
- The semantic intent of projection defaults versus omitted query values needs
  API/runtime review; Phase 0 does not infer that the current request behavior
  is a runtime bug.
- The best PowerShell shape for typed DNS record creation (`Cf*RecordInput`
  construction versus a friendlier wrapper) is a UX policy decision and must
  not be guessed from generated model readiness.
- Actual interactive user acceptance of tab completion, display width, and
  help wording remains manual evidence; the script supplements but does not
  replace that review.

## Recommended P4.1 implementation order

1. Freeze the five-command surface and resolve the pipeline identity decision
   with a compatibility-aware design note.
2. Extend the canonical help metadata/model, then generate complete MAML
   resources without hand-editing generated source.
3. Add candidate-based help and pipeline regression checks, including
   `Get-Help`, `Get-Help -Full`, `Get-Command -Syntax`, and the representative
   workflows.
4. Re-review typed DNS body construction, defaults, error guidance, and
   `ShouldProcess` wording as a PowerShell user.
5. Evaluate a compact DNS format view and narrowly scoped value completers only
   if the preceding review shows measurable user value.
6. Rebuild a fresh candidate and repeat this Phase 0 walkthrough before P4.3
   considers manual UX/help evidence complete.
