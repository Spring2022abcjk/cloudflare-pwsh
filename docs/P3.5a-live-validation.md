## DNS export contract drift

The DNS/read/export rerun reached the export endpoint successfully and
reproduced the live media type `application/octet-stream; charset=UTF-8`.
The finding is classified **E. still insufficient evidence** for choosing
between the competing explanations below.

The evidence chain is:

| Source | Observation |
| --- | --- |
| Pinned normalized operation | `GET /zones/{zone_id}/dns_records/export`, `text/plain`, raw text parsing in `fixtures/p2.2/dns-export/operations/dns-records-for-a-zone-export-dns-records.json` |
| Pinned OpenAPI | `ref/api-schemas/openapi.json` records `text/plain` for the `200` response at `/zones/{zone_id}/dns_records/export` and labels the operation as requiring DNS Read. |
| Historical Phase 0 live observation | HTTP 200, `application/octet-stream; charset=UTF-8`, and 8,933 UTF-8 bytes observed in memory only using the old account-scoped credential. This is not current P3.5a evidence. |
| First dedicated-token run | HTTP 403, `application/json`, 215 bytes, provider code `10000`; access was temporarily denied and this was not treated as an export representation. |
| DNS/read/export rerun | HTTP 200, `application/octet-stream; charset=UTF-8`, Content-Length/body length `2,607`, strict UTF-8 valid, 15 record-like lines, SOA detected. |

The successful representation is now repeatable across the current live run and
the historical Phase 0 observation, but the available evidence still cannot
distinguish A (upstream schema stale), B (multiple media types), C (correction
needed), or D (runtime should tolerate the compatible media type). Keep E as
the safe classification. The body was inspected only in memory and was not
persisted.
Cloudflare documents this as the read-only
[DNS records export method](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/export/)
and describes the broader export/import workflow in its
[DNS import/export guide](https://developers.cloudflare.com/dns/manage-dns-records/how-to/import-and-export/).

No correction, normalizer, runtime, or public API change is recommended from
the current evidence. The finding is recorded for architecture/runtime review
only; this phase does not change the normalizer, correction, runtime, retry
policy, or public API.

## Secret-handling rules

- Read only the three dedicated environment variables; never fall back to old
  credential names.
- Never accept the token on the command line or write it to a script, repo,
  transcript, exception message, test fixture, or artifact.
- Do not write account/zone IDs, domains, record IDs/names/values, raw DNS
  export, or full API responses.
- Keep any selected record ID in process memory only.
- Emit counts, booleans, status codes, media-type metadata, byte lengths,
  generic error metadata, timing, and passive rate-limit headers only.
- If configuration or candidate provenance is missing, make zero live calls.

## Blocked scenarios and risks

- The dedicated token is valid for account and zone reads, but the selected
  zone's first run returned 403/provider code `10000`; the subsequent bounded
  rerun succeeded. The transient difference is recorded, not explained by
  trying another zone.
- DNS export media-type drift is repeatable but remains classification E and

- Real-account 429 evidence is intentionally deferred.
- No permission matrix for D1 or Health Check is claimed from this run.

## Reproduction command and exit semantics

With the three dedicated environment variables securely injected and the
current-HEAD P3.4 candidate path supplied, run:

```powershell
pwsh -NoLogo -NoProfile -File .\tools\Invoke-P35ReadOnlyValidation.ps1 `
  -CandidateModulePath <approved-candidate-module-path>
```

The probe exits `2` when configuration or candidate provenance is blocked,
`3` for a partial live result, and `0` only for a complete P3.5a result. The
local boundary test can be rerun without credentials:

```powershell
pwsh -NoLogo -NoProfile -File .\tests\P35ReadOnlyValidation.Tests.ps1
```
