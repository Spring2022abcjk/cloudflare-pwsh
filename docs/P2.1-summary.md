# P2.1 Cross-Resource Generalization Summary

## Resources Tested

All fixtures come from the pinned `ref/api-schemas/openapi.json` revision and are normalized without a live Cloudflare account.

| Resource | Operations | Purpose | Result |
| --- | ---: | --- | --- |
| Zones | 5 | Collection plus ordinary resource CRUD | Confirmed normalize → correction → projection |
| D1 database | 5 | Account-scoped resource and CRUD | Confirmed `account_id` as a normal parent binding |
| AI Search namespace/instance/jobs | 4 | Deep nested resource | Confirmed account, namespace, instance, and job bindings |

Fixtures are under `fixtures/p2.1/`. Semantic snapshots are under `tests/golden/p2.1/*-semantic.json`; projection snapshots and generated metadata goldens are in the same golden directory.

## New Confirmed Facts

- **Confirmed**: A collection path can determine `List` semantics when an operation id uses a generic name such as `zones-get`; this is recorded as `CollectionPathHeuristic` with medium confidence rather than treated as raw OpenAPI fact.
- **Confirmed**: `zone_identifier` and `account_id` do not require resource-specific models. They can be represented by the existing scope binding model.
- **Confirmed**: A path can contain an arbitrary number of parent/nested bindings before its primary resource id. The selected AI Search job path records `account_id → Account (Parent)`, `name → Namespace (Nested)`, `id → Instance (Nested)`, and `job_id → Job (Primary)`.
- **Confirmed**: Collection operations ending in a literal resource segment do not have a primary resource id even when the path contains nested identifiers; those identifiers remain nested/parent bindings.
- **Confirmed**: Zones pagination is expressible by the shared `V4PagePaginationArray` model using `page`, `per_page`, `result`, and `result_info` evidence even when the response schema is built from `allOf` inline branches.
- **Confirmed**: A single generic projection path can produce consistent `Get/New/Set/Remove` cmdlet metadata for all three resources while preserving operation-specific required parameters and bindings.

## Normalizer Changes

- Generalized scope inference from fixed parameter-name cases to ordered path bindings with global scope detection, collection-vs-primary distinction, and singularized parent segment names.
- Added `zone_identifier` support and resource-path fallback for top-level `/zones`, `/accounts`, or `/users` resources.
- Split hyphenated and underscored resource path segments deterministically.
- Generalized collection semantic inference and method fallback for POST/PUT/PATCH/DELETE operations.
- Made local `$ref` resolution tolerant of trailing `/` references.
- Added stable indexes to inline `oneOf`/`anyOf`/`allOf` alternatives so sibling branches cannot collapse to the same generated name.
- Made page-array detection inspect `allOf` composition instead of requiring `collection` in a schema name.

## Model Changes

- **Confirmed**: No new normalized-model fields were required for P2.1. Existing `ResourcePath`, `ScopeBinding`, `OperationSemantic`, request/response representation, and pagination structures expressed all three resources.
- **Decision**: Keep scope binding inference in the normalizer and keep the model resource-neutral. Do not add `ZoneModel`, `AccountModel`, or `AiSearchModel` types.
- **Deferred**: `additionalProperties`/dictionary item schemas, recursive schema details, and complete OpenAPI serialization variants remain model-pressure candidates for later slices.

## API Corrections Added

- **Confirmed**: No new P2.1 API correction was added. The existing DNS DELETE correction remains the only correction applied to these test inputs.
- **Unresolved**: Zones DELETE declares an `application/json` request body in the pinned schema. P2.1 has no official wrapper evidence for changing that contract, so it remains declared and uncorrected rather than guessed away.

## Projection Changes

- Added P2.1 entries to `overrides/powershell-projection.json` for Zones, D1 database, and AI Search jobs.
- Added `tools/Project-P21Normalized.ps1`, which consumes normalized documents and projection overrides only, emits deterministic operation/cmdlet metadata, and writes generated P2.1 C# metadata.
- Preserved per-operation parameter sets, requiredness, path/query/body bindings, scope bindings, response representations, pagination strategy, `ShouldProcess`, and `ConfirmImpact`.
- **Decision**: P2.1 projection metadata is a general pipeline proof, not a commitment to expose all three resources as public handwritten cmdlets yet.

## Exceptions Found

- `zones-get` uses a generic operation id whose path is a collection; the path heuristic is required to infer `List`.
- Zones and D1 response collection envelopes use inline `allOf` branches, exposing the need for indexed inline schema identity and composition-aware pagination detection.
- AI Search job list/create paths contain an instance id but no job id; the instance binding must not be marked primary for collection operations.
- The pinned API schema contains heterogeneous response and request shapes, including operations that remain outside P2.1's runtime scope. They are recorded in fixtures but not claimed as production transport support.

## Regressions Prevented

- Existing DNS semantic diff still passes.
- Existing P1 runtime, module smoke, typed union/presence, projection, error, pagination, PUT/PATCH, and golden tests still pass.
- No resource-specific conditional was added to the existing DNS emitter; P2.1 uses a separate generic normalized projection script.
- Generated metadata compiles in the solution build.
- Snapshot comparisons are deterministic and use pinned schema input, local fixtures, and mock-free normalization.

## Still Unresolved

- Production retry/idempotency, legacy authentication, multipart, binary, streaming, complete pagination runtime strategies, full generated help, packaging, publishing, and real-account behavior.
- HTTP 2xx with `success=false` semantics.
- Final handwritten PowerShell wrapper versus generated binary `PSCmdlet` decision.
- Whether the schema-declared Zones DELETE body matches official SDK behavior.
- Complete support for every OpenAPI schema edge case and JSON Schema validation for correction/projection configuration.
