# P2.3 PowerShell Projection and Binary-Cmdlet Experiment Summary

## Scope and Evidence

P2.3 consumes the corrected normalized P2.1 fixtures for Zones, D1, and AI Search jobs. It does not read raw OpenAPI and does not change the public handwritten module. No live Cloudflare account was used.

The implementation is split deliberately:

- `tools/Project-P23Projection.ps1` emits a richer, deterministic projection for all three P2.1 resources.
- `overrides/powershell-p23-projection.json` is a P2.3 overlay; the P1/P2.1 projection baseline remains unchanged.
- `src/Cloudflare.PowerShell/Generated/Experiments/P23_GetCfZoneCommand.cs` is generated source for the isolated binary-cmdlet experiment.
- `experiments/p2.3/Cloudflare.P23.GeneratedCmdlet` compiles that source independently from the net8 main module.
- `tests/P23Projection.Tests.ps1` loads the experiment in PowerShell and records the comparison at `artifacts/p2.3/comparison.json`.

## Projection Results

- **Confirmed**: Existing verb/noun and parameter-set projection is preserved for Zones, D1, and AI Search jobs.
- **Confirmed**: API names are projected to PowerShell names by a deterministic PascalCase policy, with an explicit override for dotted query names such as `account.id` → `AccountId`.
- **Confirmed**: Scope bindings can provide `ValueFromPipelineByPropertyName`; the Zones primary `zone_id` binding becomes `ZoneId` on the `Get` parameter set.
- **Confirmed**: Output type, item/single output policy, shared-runtime paging policy, `ShouldProcess`, `ConfirmImpact`, and a structured `HelpModel` are projection metadata rather than normalized API facts.
- **Confirmed**: The generated Zones projection contains `Get-CfZone` with `List` and `Get` parameter sets, typed `Cloudflare.PowerShell.CfZone` output, item output, shared-runtime paging, and override-sourced help metadata.
- **Decision**: P2.3-specific projection policy is kept in a separate overlay so adding PowerShell UX policy does not silently rewrite P2.1 compatibility snapshots.

## Generated Cmdlet Experiment

The generated class loads as a binary `Get-CfZone` command and exposes the expected PowerShell metadata. The command body is intentionally empty: this experiment measures the public surface before adding a generic Zone runtime dispatcher.

The current comparison sample uses 100 metadata lookups in one PowerShell process:

| Dimension | Generated `Get-CfZone` | Handwritten `Get-CfDnsRecord` baseline |
| --- | --- | --- |
| Parameter sets | `List`, `Get` | `List`, `Get` |
| Typed output metadata | `Cloudflare.PowerShell.CfZone` | no `OutputType` declaration |
| Pipeline-by-property-name | `ZoneId` = true | false in the wrapper declaration |
| Help probe | command loads; rich model is in projection artifact | command loads; no rich help model |
| Non-blank source lines | 43 | 44 |
| 100 lookup sample | 13.260 ms | 9.780 ms |
| Runtime dispatch | deferred | exercised by existing mock runtime tests |

The timing is a host-local observation, not a performance claim; rerun the test to refresh it. Source size and line count are descriptive, not a complexity proof. The experiment demonstrates metadata loading and isolation, while the handwritten wrapper remains the testable runtime reference.

## Host Constraint

The current PowerShell 7.6 host exposes `System.Management.Automation` built against .NET 10. The experiment therefore targets `net10.0` independently; the production Cloudflare module remains `net8.0`. A direct net8 reference fails with `CS1705`, so this is recorded as a host/toolchain constraint rather than changing the production target.

## Unresolved and Deferred

- The generated cmdlet does not yet dispatch a Zone HTTP operation, unwrap envelopes, page results, or map API errors.
- The rich projection `HelpModel` is captured and validated as metadata; a full binary help provider/help rendering path is not implemented.
- Generated-vs-handwritten performance has only a small metadata lookup sample; no network, paging, or large-output benchmark was run.
- Public-module migration remains undecided. The handwritten module stays authoritative until generated runtime behavior has equivalent mock coverage and error/presence semantics.
- Multipart/text/binary runtime support and HTTP 2xx `success=false` semantics remain unresolved from P2.2.
