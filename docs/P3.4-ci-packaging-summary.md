# P3.4 Summary — CI, Packaging, and Release-Candidate Foundation

## Scope

P3.4 adds the release-engineering foundation on top of the completed P3.3
bounded phase. The result is a Windows-first CI workflow that restores,
validates deterministic generation, runs the existing regression/runtime
evidence, evaluates compatibility and coverage policies, assembles a module
candidate, and smoke-tests the candidate itself. It does not publish or claim
real-account, device, or manual release acceptance.

## Delivered

- `Directory.Build.props` as the assembly/package version source (`0.1.0`),
  with package-time manifest parity validation.
- `build/pinned-schema.json` and `tools/Initialize-P34Schema.ps1` for exact
  schema revision/version/hash bootstrap without tracking the external schema
  checkout.
- `tools/Test-P34Host.ps1` and a local composite CI action for the Windows,
  PowerShell 7.6+, and .NET 10 baseline.
- `tools/Invoke-P34DeterministicValidation.ps1`, which composes the existing
  P3.2/P3.3 isolated gates and P3.3 repeated coverage freshness validation.
- `tools/Invoke-P34CompatibilityGate.ps1` with exact P2.4 change allowlisting
  and explicit unknown/breaking/potentially-breaking handling.
- `tools/Invoke-P34CoverageGate.ps1` with schema, identity, determinism,
  no-drop, supported-regression, and manual-review thresholds.
- `tools/New-P34Package.ps1` for exact module staging and deterministic ZIP
  candidate assembly, plus `tests/P34PackageSmoke.ps1` for candidate-only
  import/help/metadata/mock runtime validation.
- `.github/workflows/p34-ci.yml` with separated Build, deterministic,
  unit/runtime, regression, compatibility, coverage, and package jobs; it has
  no publish step or Cloudflare secret requirement.
- `.github/workflows/p34-schema-update.yml` and
  `tools/Invoke-P34SchemaUpdateValidation.ps1` for manual, isolated schema
  update validation.
- `tests/P34CiGates.Tests.ps1` for PowerShell parse checks, policy negative
  cases, repeated package-byte checks, candidate smoke, and worktree
  preservation.

## Evidence status

The local acceptance sequence passed on 2026-09-16 in the independent
`feature/p34-ci-packaging` worktree:

- Host: PowerShell 7.6.5 and .NET SDK 10.0.400; the pinned schema revision,
  source version, and SHA-256 all agree.
- Regression: the complete P1–P2.4 chain passed, including the real revision
  diff (4 changes) and P2.3 generated-cmdlet loading from a temporary staged
  module rather than the ignored repository module DLL.
- Determinism: the P3.2/P3.3 isolated generation gates and two full P3.3
  coverage discoveries passed; both reports describe 3,407 operations and
  67,486 schemas with equal serialized output.
- Policy: compatibility passed with 4/4 exact allowlisted changes; coverage
  passed against the checked-in baseline; deliberate mutated-report negative
  cases failed as required.
- Packaging: two equal-input package assemblies were byte-identical at
  version `0.1.0`; the candidate contains four module files, and the isolated
  child-process package smoke passed import, commands, help, generated
  metadata, assembly location, and mock pagination.
- Schema update: the manual-workflow equivalent isolated validation passed
  the full regression, repeated coverage discovery, both gates, and output
  preservation check.

The package candidate is a release candidate artifact only. The following
remain outside this phase: PowerShell Gallery publishing, real Cloudflare
account behavior, device/manual UX, legacy authentication, automatic
idempotency, complete mutation retry policy, full binary PowerShell UX, and
HTTP `2xx` with `success=false` semantics.

## Candidate contract

Only the module manifest, module script, generated assembly, and generated help
resource enter `package/Cloudflare.PowerShell`. Reports and deterministic
candidate metadata are adjacent to the module, never dependencies of module
import. The package smoke child process proves that the staged assembly and
help resource—not the repository module or source tree—satisfy the import and
mock execution checks.

## Next

Future schema changes should update the pin/portable previous revision and
explicitly review compatibility allowlist and coverage baseline changes. A
later release phase may add publishing only after package, real-account,
security, and release policy evidence is separately complete.
