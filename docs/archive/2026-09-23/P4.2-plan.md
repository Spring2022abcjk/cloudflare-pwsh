# P4.2 Plan — Release & Security Hardening

## Objective

Raise the deterministic P3.4 candidate and CI foundation to a reviewable
release/security baseline without publishing, creating a GitHub Release,
expanding public admission, changing runtime semantics, or changing the P4.1
UX contract.

## Workstreams

1. Audit the existing CI and schema-update workflows for dependencies,
   permissions, fork pull requests, secrets, artifacts, and dispatch behavior.
2. Pin every external GitHub Action to a reviewed full commit SHA and keep a
   readable release comment beside each pin.
3. Make the Windows-first build inputs explicit: .NET SDK feature band,
   PowerShell fallback MSI hash, exact NuGet lock files, and locked restore.
4. Add static workflow/security checks, release metadata checks, candidate
   provenance checks, and a package secret-shaped-value boundary check.
5. Define source/schema/version/tag/Release/Gallery relationships, release-note
   inputs, Gallery preflight limitations, signing decisions, and support
   boundaries.
6. Record evidence separately for local, package, host, remote CI, real-account,
   manual UX, publishing, and final release acceptance.

## Non-goals

- No PowerShell Gallery publication or formal release.
- No real Cloudflare CRUD or live-token wiring into ordinary CI jobs.
- No broader public cmdlet admission.
- No runtime semantic or P4.1 UX changes.

## Exit rule

P4.2 is complete only when the controls are implemented and their applicable
evidence is recorded. This branch must not claim `ready for P4.3` while remote
CI, a private vulnerability-reporting channel, or any other release blocker
remains unverified.
