# P3.2 独立只读评审提示词

将下面内容复制到新的智能体会话：

```text
你是一个独立的只读评审智能体。

工作目录：
E:\桌面\edit\cloudflare-pwsh

评审对象：
当前分支上的 P3.2 任务内容及其相对于 P3.1 基线 ed00f13 的全部变更。

评审目标：
确认前两个 P1、renderer exact-drift 修复和 DNS/Zone runtime parity 是否真正按照任务目标和项目约定完成，而不是只让局部成功测试通过。

严格限制：

- 只读评审，不修改任何文件。
- 不执行 apply_patch、代码生成写入、格式化写入、迁移、删除、reset、checkout、clean。
- 不提交、不推送。
- 如果测试会修改跟踪文件，记录该事实并停止使用该测试，或仅使用隔离的临时输出。
- 不通过 `Get-Command -CommandType Cmdlet` 绕过公共命令路由问题。
- 不把 mock、runtime、host、device、real-account、manual 或 release evidence 混为一谈。
- 不因构建、静态检查或 mock 通过，就宣称真实账户、设备、发布或语义问题已经关闭。

重点评审一：公共命令路由

检查：

1. `Cloudflare.PowerShell.psd1` 和 `Cloudflare.PowerShell.psm1` 是否只把五个生成式 cmdlet 作为公共入口；同名手写函数是否仅在模块内部 helper 中存在。
2. 使用普通 `Get-Command`，不指定 `-CommandType`，检查以下命令是否全部解析为 `Cmdlet`，且普通调用确实进入生成式实现：
   - `Get-CfZone`
   - `Get-CfDnsRecord`
   - `New-CfDnsRecord`
   - `Remove-CfDnsRecord`
   - `Set-CfDnsRecord`
3. `Get-CfDnsRecord`、`Remove-CfDnsRecord`、`Set-CfDnsRecord` 是否同时保留 `DnsRecordId` 和旧脚本兼容的 `RecordId` alias，且 alias 仍绑定 API 的 dns record id path。
4. `Get-Command -All` 是否不存在同名导出函数。
5. 路由修改是否保持 parameter set、pipeline、ShouldProcess/Confirm、错误映射和输出契约。

重点评审二：canonical artifact 的完整语义

检查：

1. `artifacts/p3.2/CmdletModel.json` 是否由 `Project-P32Projection.ps1` 从 normalized/projection 输入和 P3.2 policy 生成，并且生成器没有写回它。
2. artifact 是否不仅记录 sourceFiles 哈希，还记录覆盖 cmdlet、参数、alias、operation、request/response/pagination、output、ShouldProcess 和 help 的 canonical semantic digest。
3. 在隔离副本中只修改 artifact 的 `Get-CfDnsRecord.TagAbsent.type`、alias、API binding 或 output policy，保持 sourceFiles hashes 不变；生成器是否非零失败。测试不能先重新生成 artifact 掩盖该修改。
4. 删除 canonical artifact 参数、替换 operation id、修改 request body/query binding、改变 response envelope/parsing 或 pagination stop/path 时，是否明确失败而非静默降级。
5. 是否存在“生成器自己写模型，再由测试验证自己写出的模型”的自证闭环。

重点评审三：runtime metadata 完整漂移

检查：

1. DNS 和 Zone runtime metadata 是否共用同一套完整 contract，覆盖 operation id、HTTP method/path、参数 name/location/required、request content/body/parts、response status/content/envelope/parsing、pagination strategy/request fields/response fields/result/page-info/current/total/next-cursor/has-more/next-page/stop rule。
2. 在隔离临时 DNS/Zone runtime source 中分别修改 method/path、`EnvelopePolicy`、`ParsingMode`、request representation、pagination path 和 `StopRule`，生成/契约检查是否失败。
3. mock 是否使用独立的 canonical/expected metadata，而不是先读取被测 runtime metadata 再验证自己。
4. 编译后的 `CfDnsRecordRuntimeMetadata`、`CfZoneRuntimeMetadata`/adapter 结果是否与 canonical artifact 逐项一致，尤其是 `NextCursorPath` 和 `HasMorePath`。

重点评审五：renderer exact drift 与只读入口

检查：

1. `Generate-P32Source.ps1 -ValidateOnly` 是否把当前 artifact/template renderer 输出与现有 `SourcePath` 做规范化换行后的完整内容或 SHA-256 比较；源码缺失是否失败。
2. 是否有隔离负向测试覆盖 API binding literal、operation id、body binding 或 ShouldProcess literal 漂移，并确认测试没有使用现有 generated source 作为预期结果。
3. 普通生成是否先完成 artifact、renderer、runtime 和参数消费 contract 检查，再写 generated source。
4. `tools/Invoke-P32ReadOnlyTests.ps1` 是否只在临时项目副本中生成 artifact/source/metadata/build 输出，使用普通 `Get-Command`，并在开始/结束检查工作树状态。
5. 只读入口失败时是否返回非零，并明确区分 static/generation、mock/runtime、host、device、real-account、manual、packaging/release 证据。

重点评审四：capability-driven renderer

检查：

1. `Generate-P32Source.ps1` 是否只消费 canonical artifact 和模板，公共参数、parameter set、operation id、binding、metadata、body serialization、output policy 和 ShouldProcess 是否来自 artifact。
2. 生成器中是否仍存在 `$cmdletModels`、`renderKind`、固定 operation id、按 `Get-CfZone`/`Get-CfDnsRecord` 等命令名分支，或固定假设 `Get`/`List`/`Set` 五命令形状的控制流。
3. renderer 是否基于通用 capability 字段，例如 `execution`、`parameterSets`、`operationBinding`、`invokeKind`、`bodySerialization`、`outputPolicy`，并对未知/缺失 capability 失败。
4. 当前范围可以是五个有界 cmdlet，但“范围有界”不能成为 renderer 硬编码五个命令形状的理由；检查 policy、artifact、renderer 三者职责是否分离。
5. 生成 C# 是否有手工编辑迹象；能否由模板/生成器重复生成相同内容。

验证方式：

- 阅读 P3.2 plan/progress/summary、manifest、module script、policy、canonical artifact、normalized artifact、projection、generator、template、generated source、runtime metadata 和测试。
- 使用 `git diff ed00f13..HEAD`、`git diff --check` 和必要的只读 PowerShell/.NET 检查。
- 使用普通 `Get-Command` 和普通命令调用验证公共路由。
- 对失败路径使用隔离临时副本；不要为了验证而覆盖工作树中的 artifact、generated source 或 runtime source。
- 优先运行 `tools/Invoke-P32ReadOnlyTests.ps1`；不要用会写当前工作树的
  `Invoke-P32Tests.ps1` 代替独立只读证据。
- 分别报告静态/生成、mock/runtime、host、device、real-account、manual、packaging/release 证据；不存在的证据必须明确写为未验证。

输出格式：

1. 先给结论：通过、条件通过或不通过。
2. 按严重级别列出发现：P0/P1/P2/P3。
3. 每条发现包含：文件绝对路径和行号、问题影响、可复现证据或命令、为什么现有测试没有捕获、最小修复方向。
4. 如果没有发现 P1，明确列出仍未关闭的残余风险，特别是 `2xx + success=false`、real-account、device 和 release。
5. 最后给出验收证据矩阵，区分静态/生成、mock/runtime、host、device、real-account、manual、packaging/release。
6. 不要修改代码，不要提交，不要推送。
```
