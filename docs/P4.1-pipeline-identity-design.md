# P4.1a — Pipeline Identity Design

## Decision

Use a PowerShell-only ETS identity layer for the two unambiguous resource
identities:

| Projected type | ETS alias property | Source property | Meaning |
|---|---|---|---|
| `Cloudflare.PowerShell.CfZone` | `ZoneId` | `Id` | Zone resource identity |
| `Cloudflare.PowerShell.CfDnsRecord` | `DnsRecordId` | `Id` | DNS-record resource identity |

The aliases are registered when the module is imported. They are projection
/UX metadata, not normalized API-model properties. The registration mechanism
is generic (type name + alias-property map), while the policy is explicit for
each projected type so that a future resource cannot accidentally acquire an
incorrect identity name.

No `ZoneId` alias is added to `CfDnsRecord`. A DNS record's `Id` identifies
the record; it does not contain its parent zone. Consequently these are the
supported identity workflows after this change:

```powershell
$zone | Get-CfDnsRecord
$record | Get-CfDnsRecord -ZoneId $zone.ZoneId
$record | Remove-CfDnsRecord -ZoneId $zone.ZoneId
$record | Set-CfDnsRecord -ZoneId $zone.ZoneId -Edit @{ Content = '192.0.2.10' }
```

The following remains explicitly unsupported because the required parent
scope is unavailable from the output object:

```powershell
$record | Remove-CfDnsRecord
$record | Set-CfDnsRecord -Edit @{ Content = '192.0.2.10' }
```

PowerShell must report the missing mandatory `ZoneId`; the module must not
guess a zone from a record name or record ID.

## Evidence before implementation

The Phase 0 candidate exposed `CfZone.Id` and `CfDnsRecord.Id`, while the
generated parameter metadata required `ZoneId` and/or `DnsRecordId` by
property name. `$zone | Get-CfDnsRecord` therefore failed before HTTP
dispatch. The Phase 0 report records the reproduction and the exact
five-command public surface in [`P4.1-ux-readiness.md`](P4.1-ux-readiness.md).

Synthetic PowerShell 7.6.5 host tests established two relevant facts:

1. `[Alias('Id')]` on a parameter does participate in
   `ValueFromPipelineByPropertyName` binding.
2. `Id` cannot be declared as an alias for both `ZoneId` and
   `DnsRecordId` in one command. PowerShell rejects the command metadata
   with `The alias "Id" is declared multiple times.`

The latter makes a parameter-only design unable to express both resource
identities for `Get-CfDnsRecord`, where `ZoneId` and `DnsRecordId`
coexist.

An ETS synthetic host test also established that an `AliasProperty`:

- binds through `ValueFromPipelineByPropertyName`;
- appears in `Get-Member`, so the identity is discoverable;
- is visible to `ConvertTo-Json` and `PSSerializer` as an extended member.

The serialization observation is an intentional compatibility consideration,
not an invisible implementation detail. It is additive PowerShell object
metadata and does not change the generated C# API model or the HTTP request
body/query construction. The compatibility report and candidate tests must
continue to treat the extended member as part of the PowerShell UX contract.

## Alternatives

### Option A — Additive model alias properties

Add `ZoneId` or `DnsRecordId` to the generated C# model and map it to
`Id`.

This would make the pipeline experience simple, but it pollutes the API model
with PowerShell naming and creates a second public property in typed output.
It also changes normal .NET/PowerShell serialization and would require model
projection, generated source, output-shape, and compatibility updates for
every affected resource. It is rejected because the identity aliases are a
PowerShell UX concern rather than facts in the normalized API model.

### Option B — Parameter aliases

Use `[Alias('Id')]` on the consuming parameter(s). This is a real PowerShell
binding mechanism, as confirmed by the synthetic test, but it cannot alias
`Id` to both `ZoneId` and `DnsRecordId` in `Get-CfDnsRecord`. Choosing
one would make the other identity less correct, and omitting one would leave
a declared workflow inconsistent. It also cannot solve the missing parent
scope for record mutation. Rejected as the primary design.

### Option C — ETS / TypeData alias properties

Register `ZoneId -> Id` and `DnsRecordId -> Id` only for the projected
PowerShell output types. This keeps the normalized/API model clean, supports
the two resource identities without alias collisions, and works for any
consumer that uses standard PowerShell property-name binding. The registration
is deterministic and candidate-packaged through the module loader.

The trade-off is that `Get-Member`, `ConvertTo-Json`, and PowerShell object
serialization expose the additive extended aliases. This is documented and
tested as PowerShell output metadata; it is not presented as a new API-model
field. Module-loading and serialization behavior are included in candidate
smoke coverage.

The module registers the aliases from generated pipeline-identity metadata
during import with Update-TypeData -Force. Re-import is therefore deterministic
and does not duplicate members. PowerShell TypeData is session-scoped; removing
a module does not provide a safe member-level cleanup primitive, so callers
should treat the aliases as available after importing the module in the current
session. A broad Remove-TypeData cleanup was intentionally not added because
it could remove unrelated user TypeData for the same .NET type.

### Option D — Explicit wrapper/adaptor

Return a PowerShell wrapper carrying API data plus UX identity properties.
This gives precise control over the UX surface, but changes the concrete
output type, complicates typed output compatibility and formatting, and risks
breaking callers that expect `CfZone` or `CfDnsRecord`. Rejected for this
phase.

### Option E — Remove the misleading pipeline declaration

Stop declaring `ValueFromPipelineByPropertyName` and require explicit IDs.
This would be truthful, but it removes a useful and implementable PowerShell
workflow and changes parameter metadata for all affected commands. It remains
the fallback if the identity layer cannot be made deterministic; it is not
needed after the ETS evidence above.

## Compatibility evaluation

| Compatibility surface | Effect of the chosen design | Classification |
|---|---|---|
| Pipeline binding | Adds the intended `Id -> ZoneId` and `Id -> DnsRecordId` property-name paths | Behavioral, additive |
| Output shape | C# properties remain unchanged; PowerShell adds ETS aliases | Potentially compatibility-sensitive |
| Public model properties | No generated model changes | Non-breaking model-wise |
| Parameter metadata | Existing declarations remain; no rename/set change | Non-breaking metadata addition through object projection |
| Serialization | ETS aliases appear in PowerShell JSON/CLIXML serialization | Potentially compatibility-sensitive; documented and tested |
| HTTP semantics | No request construction or API operation changes | Unchanged |
| Help contract | Must state resource identity versus required parent scope | Additive help contract |

This is not a command rename, parameter rename, parameter-set redesign,
mandatory-parameter change, output-type replacement, or ShouldProcess change.
The `ZoneId` requirement for record mutations remains mandatory; only the
record identity can be supplied from a `CfDnsRecord` object.

## Test obligations

Host and fresh-candidate tests must prove all of the following separately:

- `$zone | Get-CfDnsRecord` succeeds and dispatches with the zone ID.
- `$record | Get-CfDnsRecord -ZoneId ...` supplies only the record identity
  from the pipeline and the parent scope explicitly.
- `$record | Remove-CfDnsRecord -ZoneId ...` and the analogous Set workflow
  bind the record ID while retaining explicit scope.
- `$record | Remove-CfDnsRecord` and Set without `-ZoneId` fail clearly
  before dispatch because scope is mandatory.
- `Get-Member`, `ConvertTo-Json`, and candidate import expose the documented
  ETS identity behavior.
- No HTTP mutation is made by any WhatIf workflow.

The design does not add public cmdlets, aliases, parameter names, or API
operations. Formatting views and argument/value completers remain outside this
decision and are deferred unless later evidence makes one a low-risk,
high-value follow-up.
