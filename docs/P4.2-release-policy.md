# P4.2 Release, Version, Tag & Notes Policy

## Single version source

`Directory.Build.props:VersionPrefix` is the only version source. The current
value remains `0.1.0`; P4.2 does not change it.

| Output | Rule |
| --- | --- |
| `VersionPrefix` | Stable numeric `major.minor.patch`; current `0.1.0`. |
| `Version` | Derived from `VersionPrefix`. |
| `AssemblyVersion` | `VersionPrefix.0`; changing it is a binary-identity decision. |
| `FileVersion` | `VersionPrefix.0`. |
| Assembly informational version | `VersionPrefix+source.<40-character commit SHA>`. |
| Module manifest `ModuleVersion` | Exact three-part `VersionPrefix`; current `0.1.0`. |
| Stable candidate ZIP | `Cloudflare.PowerShell.<VersionPrefix>.zip`. |
| Stable Git tag | `v<VersionPrefix>`, created only from the approved clean commit. |
| GitHub Release | Uses the exact stable tag; a release is not created by validation CI. |
| Gallery version | Must equal the module manifest version. The first public release is a separate publish gate. |

## 0.x and prerelease policy

The `0.x` line is preview software and does not promise stable compatibility.

- Patch bump: compatible bug fix, packaging/security correction, or narrowly
  scoped documentation/metadata correction.
- Minor bump: new capability or any breaking public/runtime/API-projection
  behavior while the project remains on `0.x`; the breaking change must be
  called out in release notes.
- Major bump: reserved for the post-preview compatibility policy.
- Prerelease label: `preview.N`, monotonically increasing per base version.
  A future Gallery prerelease uses numeric `ModuleVersion` plus
  `PrivateData.PSData.Prerelease = 'preview.N'`; its tag is
  `v<base-version>-preview.N` and its candidate filename is
  `Cloudflare.PowerShell.<base-version>-preview.N.zip`.

The current P3.4 package builder accepts the stable three-part candidate
`0.1.0`. Prerelease packaging must extend and test that builder and manifest
contract before a prerelease is enabled; this policy does not silently change
the current candidate.

## Tag and release controls

1. Start from a clean checkout and record the exact source commit.
2. Verify the pinned schema, all P1–P4.1 applicable gates, package provenance,
   security review, support matrix, and release notes.
3. Create the tag only after final approval; verify the tag resolves to the
   approved commit and that no validation workflow can publish from a PR.
4. Create a GitHub Release from that tag only as an explicit release action.
5. Publish to Gallery only in a separately protected job after Gallery
   preflight, signing decision, and final approval pass.

## Release-note inputs

Release notes are assembled from existing semantic artifacts and a short
curated section, not from hand-editing generated source:

- P2.4 compatibility report and exact allowlist summary;
- P3.2/P3.3 public-admission and coverage summaries;
- P3.1 runtime changes and known semantic limitations;
- P3.5 real-account results, if any, kept separate from mock evidence;
- P4.1 manual UX/help result;
- P4.2 security, supply-chain, provenance, support, and signing decisions;
- supported environments and explicit breaking changes;
- known limitations and deferred behaviors.

Use [`release-notes-template.md`](./release-notes-template.md) as the review
input. The template is not a release announcement and does not authorize
publishing.

## Gallery preflight and signing decision

Gallery preflight may validate the manifest, exact module contents, version,
metadata, tags, release notes, and token presence without printing the token.
The staged module should first pass `Test-ModuleManifest` and local package
checks. PowerShellGet also exposes `Publish-Module -WhatIf -Verbose` as a
local command-plan check, but that is not a remote Gallery acceptance result
and must not be reported as a publish. A future release job must use a
protected API key with the minimum required scope and run only after explicit
approval. This branch does not invoke `Publish-Module` against any Gallery.

The authoritative Microsoft guidance used for this design is the [Gallery
FAQ](https://learn.microsoft.com/en-us/powershell/gallery/faqs?view=powershellget-3.x),
[module manifest guidance](https://learn.microsoft.com/en-us/powershell/scripting/developer/module/how-to-write-a-powershell-module-manifest?view=powershell-7.5),
and [package publishing guidance](https://learn.microsoft.com/en-us/powershell/gallery/how-to/publishing-packages/publishing-a-package).
They establish the manifest/license metadata boundary, `ProjectUri`/
`LicenseUri`/`Tags`/`ReleaseNotes`/`Prerelease` fields, API-key requirement,
`Test-ModuleManifest`, and the limits of `-WhatIf` as a preflight.

Current signing decision: **Explicitly deferred for the first public release**.
The first release is a Windows-first PowerShell module containing a managed
assembly and PowerShell module files, not a native executable or installer.
Requiring Authenticode now would introduce certificate acquisition, protected
CI key custody, rotation, and verification dependencies without changing the
local package provenance chain already required by this phase. The accepted
risk is that consumers must rely on the approved Git commit, schema identity,
candidate manifest, package hash, and Gallery transport controls rather than a
publisher certificate.

Revisit this decision before the first public release if any of the following
becomes true: an enterprise distribution requirement mandates Authenticode; a
native executable/installer is added; the release threat model requires signed
PowerShell files or assemblies; or a protected signing architecture and
certificate verification procedure are approved. Until then, no certificate is
requested, generated, uploaded, or used by CI.
