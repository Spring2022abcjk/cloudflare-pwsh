## DNS export media-type investigation — 2026-09-26

The pinned OpenAPI/normalized response declares HTTP 200 `text/plain` with
raw-text parsing. The current official
[TypeScript export method](https://github.com/cloudflare/cloudflare-typescript/blob/main/src/resources/dns/records.ts)
returns a string and sends `Accept: text/plain`; the pinned Python and Go
SDKs do the same. Cloudflare's
[API reference](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/export/)
describes a BIND export, and its
[DNS guide](https://developers.cloudflare.com/dns/manage-dns-records/how-to/import-and-export/)
shows a GET yielding a zone file. Those pages do not establish that every
successful response uses the `text/plain` header.

The request headers differ across the initial observations: the P3.5a direct
probe set no `Accept` header; the six-GET P3.5c tranche used
`Accept: application/json`. The separately approved two-GET comparison below
then tested `Accept: text/plain` against `Accept: application/json` under
the same token and zone. Both returned the same octet-stream media type.
Thus these two `Accept` values did not change the response media type in
the tested scope. Other server conditions remain untested. The current
runtime selects
response metadata by status and media type, then falls back to the first
matching status when media type differs
([code](../src/Cloudflare.PowerShell/Runtime/CloudflareRuntimeAbstractions.cs)).
The focused local mock now confirms that the fixed text representation parses
valid UTF-8 export bytes with an octet-stream response header; the 18-case
runtime assertion program passed on 2026-09-26. This is mock/local evidence,
not a live candidate-cmdlet export result. DNS export is outside the five
formal cmdlets.

| Option | Evidence or change needed | Decision boundary |
| --- | --- | --- |
| Record a known upstream media-type discrepancy | Keep the pinned contract and observed header separate; document valid text shape and the absence of a public export cmdlet. | Accepted by the owner on 2026-09-26 for bounded P3.5c closure; no runtime/schema change. |
| Test `Accept` negotiation | Completed on 2026-09-26 under separate authorization: two serial GETs to the same approved zone's export endpoint, one `Accept: text/plain`, one `Accept: application/json`. | Both returned octet-stream; no negotiation difference was observed for these headers in this scope. This does not prove behavior for every zone. |
| Propose a future code correction | If independent evidence establishes an actual user-facing failure or schema defect, first design an operation-specific compatibility rule and regression test. | Requires a separately approved runtime/schema change; never reinterpret all octet-stream responses as text. |

### Sanitized Accept comparison — 2026-09-26

The [dedicated comparison probe](../tools/Invoke-P35cExportAcceptComparison.ps1)
sent exactly two serial GETs, at 06:44:38 and 06:44:41 UTC, to the same
approved export endpoint. `Accept: text/plain` and
`Accept: application/json` each returned HTTP 200,
`application/octet-stream; charset=UTF-8`, 2,609 bytes, strict UTF-8
validity, and an SOA-record shape match. No response body, zone identifier,
domain, record data, or credential was persisted. There was no retry,
redirection, mutation, or additional request.

The comparison rules out the tested `Accept` difference as the cause of
the header drift in this scope. It does not identify whether the provider
implementation, its published schema, or another response layer should be
corrected. Recommended P3.5c disposition: accept the header mismatch as a
documented known limitation for the current five-cmdlet candidate, retain
`text/plain` as the pinned contract, and open any upstream/schema/runtime
correction only after separate evidence and approval. The owner accepted this
disposition on 2026-09-26; the upstream cause remains unresolved.
