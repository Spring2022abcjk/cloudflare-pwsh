# P3.3 Plan — Coverage Discovery and Bounded API Expansion

## Status and decision

P3.3 is the active coverage-expansion phase after the validated P3.2
representative public surface. This plan is implementation-oriented and keeps
the P3.2 public artifact and generated source authoritative for the existing
five-cmdlet slice until a new slice passes the same evidence gates.

The first bounded expansion slice selected from the pinned baseline is the
`d1/database` family. It contains six operations: the five existing P2.1 D1
operations plus `d1-update-partial-database`. The slice is intentionally an
incremental family extension, not a second DNS/Zone demonstration.

## Goal

P3.3 establishes a repeatable path from the full pinned OpenAPI document to an
explainable operation-coverage report and then expands one bounded resource
family through the existing normalized, corrected, projected, canonical, and
generated chain.

The phase must provide:

- global coverage discovery over every operation accepted by the normalizer;
- explicit operation classification with evidence and missing capabilities;
- deterministic JSON and Markdown coverage reports;
- projection and generator capability-gap detection;
- a bounded D1 extension slice with account scope, CRUD, pagination, and PATCH;
- compatibility visibility for any new public projection;
- reusable tests and a read-only validation entry point.

## Non-goals

P3.3 does not include:

- module publishing, packaging, or a complete release pipeline;
- unrestricted generation of the entire Cloudflare API;
- full real-account or device coverage;
- deciding all unresolved runtime policies, including `2xx + success=false`,
  legacy authentication, automatic idempotency, or complete mutation retry
  safety;
- weakening typed models to `object` merely to increase a coverage number;
- replacing the P3.2 artifact or declaring full-module migration complete;
- resource-specific generator renderers or endpoint-specific transport logic.

| Dependency | Required capability | P3.3 use |

| P1/P2 normalized architecture | Normalized operations, schemas, scope bindings, representations, pagination, provenance | Discovery input and operation-level facts |
| API correction system | Contract corrections with traceable rule/reason/source | Distinguish interpreted API facts from source declarations |
| PowerShell projection | Verb/noun, parameter names, parameter sets, pipeline and UX policy | Candidate public surface and projection diagnostics |

| .NET 10 / PowerShell 7.6 | Supported Windows-first host baseline | Build and host validation baseline |

## Coverage stages and classification

Discovery reports these stages independently:

1. **Normalization** — the operation is present in the corrected normalized
   document with method, path, semantic provenance, parameters, responses, and
   required representation data.
2. **Correction** — zero or more explicit API correction rules are recorded;
   correction is not inferred from a projection or runtime failure.
3. **Projection** — deterministic default or override-based PowerShell names
   and parameter sets can be constructed without parameter-name or
   parameter-set collisions.
4. **Runtime** — all declared method, request representations, response
   parsing/envelopes, and pagination strategies are covered by existing shared
   runtime capabilities. Runtime readiness does not prove typed model or public
   UX readiness.
5. **Public eligibility** — the operation is admitted to the bounded public
   policy, has a complete canonical operation binding/output policy, and passes
   generated-source and mock parity gates.

Normalization success, projection construction, and C# generation are not by
themselves `Supported`.

The final classification vocabulary is:

| Classification | Meaning |
| --- | --- |
| `Supported` | Public-eligible operation passes all stages without an operation-specific correction or projection override. |
| `SupportedWithOverride` | Public-eligible operation passes all stages and explicitly records an API correction and/or projection policy. |
| `UnsupportedRuntimeCapability` | A shared runtime serializer, parser, envelope, pagination, or HTTP capability is missing. |
| `UnsupportedProjectionCapability` | PowerShell name/parameter-set/output/public binding cannot be represented by the current projection contract. |
| `UnsupportedNormalizationCapability` | The normalized IR cannot faithfully express the API contract. This must trigger model analysis, not an override workaround. |
| `AmbiguousSemantics` | The operation semantic kind is unknown or contradictory. |
| `ExcludedByPolicy` | The operation is deliberately outside the current bounded public admission policy; this is not a permanent unsupported claim. |
| `NeedsManualReview` | Evidence is insufficient for safe automatic admission, such as low-confidence semantic inference or unclear public UX. |

Every scanned operation must have exactly one final classification. Each row
also records `reasonCodes`, `missingCapabilities`, resource family, operation
id, method/path, semantic source/confidence, normalized/correction/projection/
runtime status, correction rules, override involvement, projected cmdlet/set,
and current public cmdlet mapping.

Stage counts are intentionally independent and therefore do not have to equal
the final-classification counts. Final classification records the first
actionable blocker in this order: semantic ambiguity, projection conflict,
runtime gap, current public eligibility, then bounded-policy exclusion.

## Coverage report contract

The machine-readable report is `artifacts/p3.3/coverage-baseline.json`. Its
deterministic schema is:

```text
schemaVersion
stage
sourcePath
sourceRevision
deterministic
generatedAt                 # null; no wall-clock value in artifacts
normalizedSchemaCount
totalOperations
countSemantics             # normalized schema, runtime-ready stage, final runtime classification meanings
inputIdentity              # deterministic hashes for source, corrections, projection policy, and public artifact
stageCounts
classificationCounts
capabilityGapCounts
resourceFamilyCounts[]      # family, totalOperations, classificationCounts
operations[]                # one complete row for every scanned operation
```

The report deliberately keeps a null `generatedAt` field out of the semantic
identity of the artifact; a timestamp must never create false diff noise.
`inputIdentity` records the normalized source path/revision/SHA-256 and the
correction, projection-policy, and current-public-artifact input hashes.
`countSemantics.normalizedSchemaCount` counts normalized schemas, while
`countSemantics.runtimeReadyStageCount` counts operations that pass the shared
runtime capability stage. `countSemantics.finalUnsupportedRuntimeCapabilityCount`
counts only rows whose final classification is
`UnsupportedRuntimeCapability`; it is intentionally not the same as the
runtime stage's total gap count when an earlier projection or semantic blocker
determines the final classification.
`operations[]` is sorted by the ordinal operation identity key
`operationId|method|pathTemplate`; reason codes and capability lists
are sorted; resource-family rows are sorted by family. The report is therefore
safe to compare byte-for-byte after the same source and policy inputs.

The Markdown report has the same source identity and shows total/stage counts,
classification counts, reason counts, all resource-family summaries, current
supported operations, and bounded examples for runtime gaps and manual review.
The JSON report remains the complete machine-readable record.

## Baseline discovery

The baseline is produced by `tools/Invoke-P33CoverageDiscovery.ps1`. It calls
the existing normalization and correction libraries directly, builds the
existing generic projection model, detects projection parameter-name and
parameter-set collisions, checks current shared-runtime representation
capabilities, and reads the P3.2 canonical artifact for current public
operation membership.

The first pinned baseline produced:

| Measure | Result |
| --- | ---: |
| Source revision | `4.0.0` |
| Normalized schemas | `66,580` |
| Operations | `3,407` |
| Normalized successfully | `3,407` |
| Correction-applied operations | `1` |
| Runtime-ready stage operations | `3,382` |
| Runtime capability-gap stage rows | `25` |
| Projection conflicts | `568` |
| Current public operations | `8` across `5` cmdlets |

The baseline discovery gate is green. During this discovery step the P3.2
read-only gate exposed a portability defect: source freshness hashes depended
on the checkout's CRLF/LF byte representation. `tools/P32Hash.ps1` now hashes
UTF-8 text after canonicalizing line endings, and both projector and generator
use that helper. The P3.2 canonical artifact was regenerated under the same
policy; the independent P3.2 read-only acceptance gate is green without
resetting or checking out the `skip-worktree` inputs.

Final classification counts are:

| Classification | Count |
| --- | ---: |
| `SupportedWithOverride` | 8 |
| `UnsupportedProjectionCapability` | 491 |
| `UnsupportedRuntimeCapability` | 10 |
| `NeedsManualReview` | 617 |
| `ExcludedByPolicy` | 2,281 |

There are currently no `AmbiguousSemantics` or
`UnsupportedNormalizationCapability` rows in this baseline. Those categories
remain part of the contract so a future normalizer failure cannot disappear
from the report or be silently disguised as a projection override.

The `66,580` normalized-schema inventory, `3,382` runtime-ready stage count,
and final `UnsupportedRuntimeCapability=10` classification count are separate
measures; they must not be reported as interchangeable coverage totals.

## Typed model schema parity gate

Every public P3.3 model is bound in the projection policy to one or more
normalized schemas and an explicit `request` or `response` direction. Every
model property records its normalized source schema/property, JSON name,
expected C# type, nullable state, presence state, and nested model reference
when applicable. `tools/P33ModelSchemaParity.ps1` verifies these declarations
against the normalized D1 fixture before the canonical artifact is emitted;
the generator repeats the check against the canonical artifact. `object`,
`System.Object`, and `PSObject` are rejected by default. A future object
fallback requires an explicit allowlist entry with reason, source, and
provenance plus a negative/positive test.

## First expansion slice: D1 database extension

### Rationale

`d1/database` is selected because the baseline gives it six high-confidence,
runtime-ready operations and no default parameter-name collision. It extends
the already normalized P2.1 family with a PATCH operation, so it tests
incremental family expansion, operation-set merging, account scope, body
presence, and mutation safety without introducing a new transport class. It is
large enough to test scale, but small enough to stop before the whole D1 API or
the whole Cloudflare API.

The existing five operations are evidence inputs, not a reason to bypass the
P3.3 gates. The new operation must be projected into the same public noun and
must not create a second accidental `Set-D1Database` surface beside
`Set-CfD1Database`.

### Exact scope

```text
d1-create-database
d1-delete-database
d1-get-database
d1-list-databases
d1-update-database
d1-update-partial-database
```

Expected contract facts from the baseline are account scope for every
operation, JSON request bodies for create/update/partial-update, shared page
parameters for list, and JSON responses. The slice does not include D1 query,
database contents, export, or unrelated D1 families.

### Planned slice artifacts

- a pinned six-operation normalized fixture derived from the full normalized
  document, without hand-editing raw OpenAPI;
- a P3.3 projection policy that aligns the partial update with the existing
  D1 public noun and gives it an unambiguous parameter set;
- a P3.3 canonical slice artifact with semantic digest and complete operation,
  parameter, body, output, and runtime metadata;
- generated model/metadata/PSCmdlet source only through a capability-driven
  renderer; no D1-specific renderer branch;
- deterministic projection/source validation and mock/runtime smoke tests;
- compatibility input/report coverage for the expanded public projection.

### Slice acceptance gate

The slice may be called complete only when:

1. all six operations are present exactly once in the fixture and coverage
   report;
2. the partial operation has explicit, evidence-backed projection alignment;
3. account scope, PATCH method/path, JSON body presence, output type, and
   pagination metadata agree across normalized data, canonical artifact,
   generated source, and runtime metadata;
4. generated code contains only binding, parameter-set, `ShouldProcess` where
   applicable, metadata dispatch, and shared-runtime calls;
5. mock HTTP tests cover list paging, get, create, delete, PUT update, PATCH
   update, request bodies, typed output, and stable errors;
6. projection compatibility sees the new public command and its parameter-set
   changes;
7. the isolated read-only validation copies only required input files (without
   VCS metadata, `bin`, or `obj`), reproduces artifacts/source, stages the
   smoke module outside the repository, and leaves the worktree unchanged; and
8. the complete P1/P2.1/P2.2/P2.3/P2.4/P3.1/P3.2 regression chain passes.

## Correction, model, projection, runtime, and policy decisions

- Use an API correction only when pinned/official contract evidence shows that
  the normalized API interpretation is wrong. Preserve a correction trace.
- Change the normalized model when the same contract structure is missing for
  multiple APIs or the existing IR cannot faithfully represent the D1 contract.
  Do not hide a model deficiency in a resource-specific override.
- Use a projection override for public PowerShell naming, parameter-set
  alignment, typed output policy, pipeline policy, confirmation, or help. Keep
  it separate from API corrections.
- Record `UnsupportedRuntimeCapability` when the blocker is a genuinely shared
  serializer/parser/pagination/runtime feature. Implement that capability in
  shared runtime only if it is general, bounded, and necessary for this slice;
  otherwise leave the operation classified and stop expansion.
- Record `NeedsManualReview` when public UX, output shape, or semantic intent
  cannot be safely inferred. Do not force a cmdlet name for coverage metrics.

## Stop conditions

Stop expanding the D1 slice and summarize before changing scope if any of the
following occurs:

- the normalized model cannot faithfully express a D1 operation;
- a normal API behavior requires `if resource == ...` or `if operationId == ...`
  in the generator or runtime;
- projection overrides become numerous enough to conceal a missing general
  naming/parameter-set rule;
- a required capability is an unrelated new P3.1 runtime project rather than
  a small general extension;
- typed output would have to degrade to `object` without contract evidence;
- public UX or operation semantics remain ambiguous;
- correction evidence is missing, especially for request-body/presence
  interpretation;
- any P1/P2/P3.1/P3.2 regression fails;
- deterministic artifact/source reproduction or clean-worktree validation
  fails.

The unresolved `2xx + success=false` behavior and other deferred runtime or
real-account policies remain unresolved regardless of local mock results.

## Tests and validation entry point

The discovery slice uses:

```text
CoverageClassificationTests
CoverageReportDeterminismTests (fresh A/B, checked-in JSON/Markdown freshness,
input identity, and mutated source/count rejection)
UnsupportedReasonTests
ProjectionCoverageTests
GeneratedSourceValidation
SelectedSliceRuntimeSmoke
ExistingRegressionChain
```

The discovery script is read-only with respect to source inputs and emits only
the requested P3.3 reports. The eventual slice acceptance must add an isolated
temporary-project validation entry point following the P3.2 read-only pattern.

## P3.3 completion criteria

P3.3 is complete only when the coverage pipeline is deterministic and every
scanned operation is classified, the baseline and bounded-slice reports are
reproducible, unsupported reasons are actionable, the D1 extension passes its
slice gate, new public projection is visible to compatibility checks, all
regressions pass, and documentation records implemented/validated/deferred
evidence separately. A high percentage or a high generated-cmdlet count is not
itself an acceptance criterion.
